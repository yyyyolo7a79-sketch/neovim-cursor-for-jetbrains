## 効果

カーソルが移動すると：

- **トレイル**：カーソルが不規則な四角形に「引き伸ばされる」（バネモデル）
- **スムーズな追従**：減衰バネで駆動され、瞬時のジャンプではない
- **グロー**：縁に沿った柔らかなハロー（Canvas の `shadowBlur` を模擬）。**トレイルの展開に応じて点灯し、カーソルが静止すると自動的に消灯**
- **ネイティブカーソルの非表示**：トレイルとの重なりを回避

パラメータの意味は VS Code 版 `neovide-cursor` と揃えてあり、プラットフォームをまたいで設定を移行しやすくなっています（唯一の例外は[パラメータ設定](#パラメータ設定)を参照）。

### 2 つのトレイルモデル（メニューからいつでも切り替え可能）

| モード | 仕組み | 特徴 |
|---|---|---|
| **バネ**（デフォルト） | カーソル矩形の 4 つの角点それぞれに減衰バネを 1 組ずつ取り付け、運動方向に応じて異なる遅延係数を割り当てる → 矩形が引き伸ばされる | Neovide 原本の効果。フレーム間補間に依存 |
| **残像** | カーソルの実際の位置を毎フレーム記録し、フェードする残像を連ねて描画する | **フレーム落ちでも破綻しない**。低フレームレートでより安定し、グローの見え方はバネモードよりはっきりしている |

両者は同じ基盤（オーバーレイのマウント、ネイティブカーソルの非表示、高精度スケジューリング、部分再描画）を共有し、
異なるのは「位置計算」の部分だけです。

## インストール

### 方法 1：Release からダウンロード（推奨）

1. [Releases](https://github.com/yyyyolo7a79-sketch/neovim-cursor-for-jetbrains/releases) から最新の `*.zip` をダウンロード
2. IDEA → `Settings` → `Plugins` → `⚙️` → `Install Plugin from Disk...`
3. その zip を選択し、IDE を再起動

### 方法 2：自分でビルドする

```bash
# 要件：JDK 21、Gradle 9.0+、IntelliJ Platform Gradle Plugin 2.x
./gradlew buildPlugin
# 成果物：build/distributions/*.zip
```

ローカルにインストール済みの IDE を使う場合（数 GB の配布パッケージをダウンロードせずに済みます）は、`build.gradle.kts` を次のように変更します：

```kotlin
dependencies {
    intellijPlatform {
        local("D:/path/to/IntelliJIdea2025.2")   // 自分のインストールパスに置き換える
    }
}
```

## 互換性

**サポート範囲：2024.2 ~ 2026.2 以降**

| IDE | バージョン | 状態 |
|---|---|---|
| IntelliJ IDEA | 2024.2 – 2026.2 | ✅ 実機検証済み |
| CLion | 2025.2 | ✅ 実機検証済み |
| PyCharm | 2025.2 | ✅ 実機検証済み |

**なぜ IDE をまたいで共通に動作するのか**：本プラグインは `com.intellij.modules.platform`
（プラットフォームの中核モジュール）にのみ依存しており、言語固有の API には一切触れず、IDEA Ultimate の専有機能にも依存していません。
したがって 2024.2+ のすべての JetBrains IDE ——
WebStorm / PhpStorm / GoLand / RubyMine / Rider / DataGrip など —— で動作します。

### バージョン下限が 2024.2 である理由

2024.2 はプラットフォームが **JBR 21** に切り替わった起点であり、本プラグインのコンパイルターゲット（Java 21）と一致します。
2024.1 以前は **JBR 17** 上で動作するため、Java 21 のバイトコードを読み込むと
`UnsupportedClassVersionError` を投げて即座にクラッシュします —— これはバイトコードレベルの厳格な制約であり、API とは関係ありません。

### バージョン上限を設けない理由

`<idea-version since-build="242" />` では `until-build` を**意図的に省略**しています。
本プラグインはバージョン固有のコードを一切含まないため、以降のバージョンにも自然に互換であり、空欄は「すべての新しいバージョンに適用される」ことを意味します。

> これは JetBrains 公式が推奨する書き方です。上限を固定すると（かつての `252.*` のように）、
> **IDE をアップグレードするたびにプラグインが「非互換」と判定され**、ユーザーは新バージョンのリリースを待つしかありません ——
> 本プラグインの初期バージョンはまさにここでつまずきました。詳細は落とし穴 #17 を参照。

### もっと古いバージョンをサポートしたい場合

コンパイルターゲットを、対象プラットフォームに内蔵された JBR のバージョンまで下げる必要があります：

| IDE バージョン | build | 内蔵 JBR | 必要なコンパイルターゲット |
|---|---|---|---|
| 2022.x | 221–223 | 11 | Java 11 |
| 2023.x | 231–233 | 17 | Java 17 |
| 2024.1 | 241 | 17 | Java 17 |
| **2024.2+** | **242+** | **21** | **Java 21（現在）** |

良い知らせとして、**低いバージョンのバイトコードは高いバージョンの JBR で読み込めます** ——
コンパイルターゲットを下げても、現在サポートしている 2024.2~2026.2 には影響しません。純粋な拡張です。

## 使い方

- **オン/オフ**：`Tools` メニュー → `Neovide 拖尾光标（开关）`
- **トレイルモデルの切り替え**：`Tools` メニュー → `Neovide 光标：残影模式（低帧率更稳）`
  - **チェックあり** = 残像モード、**チェックなし** = バネモード（Neovide 原本の効果）
  - **即時反映**、IDE の再起動は不要
- **パフォーマンス診断**：`Tools` メニュー → `Neovide 光标：性能诊断（禁用重绘）`
  - チェックするとすべての描画をスキップし、物理計算だけを実行します。「描画が遅い」のか「スケジューリングが遅い」のかを切り分けるためのものです —— **これは非常に有用な調査手段です**

スイッチをオフにすると、ネイティブカーソルが即座に復元され、オーバーレイが削除されます。

## パラメータ設定

全パラメータは `core/NeovideConfig.java` にあり、命名と意味は VS Code 版 `neovide-cursor.js` の `cursorConfig` に揃えています：

| パラメータ | デフォルト値 | 説明 |
|---|---|---|
| `tailColor` | `#FFC0CB` | トレイルの色 |
| `useShadow` / `shadowColor` | `true` / `#FFC0CB` | グローのオン/オフと色 |
| `shadowBlurFactor` | `0.2` | グローの外拡半径 = この係数 × カーソルの長辺（**原本の 0.6 から変更済み。理由は落とし穴 #15**） |
| `animationLength` | `0.1` | 通常のアニメーション時間（秒）。大きいほどトレイルが長くなる |
| `shortAnimationLength` | `0.05` | 短距離移動のアニメーション時間 |
| `shortMoveThreshold` | `8` | 短距離判定のしきい値 |
| `trailFactors` | `1 / 0.9 / 0.5 / 0.3` | 四隅の遅延係数（トレイル伸長の中核） |
| `useHardSnap` / `leadingSnapThreshold` | `true` / `0.5` | 前縁の角のハードスナップ |
| `maxTrailDistanceFactor` | `60` | トレイル最大長の係数。原本と一致（落とし穴 #6 を参照） |
| `glowLayers` / `glowOpacity` | `12` / `0.55` | グローの層数とピーク強度（**層数は明るさに影響しません**。後述の「グローのシミュレーション」を参照） |

> `shadowBlurFactor` を除き、この表は原本の `cursorConfig` と**項目ごとに一致**しています。
> ハローが大きすぎる／小さすぎると感じた場合は、`shadowBlurFactor` の 1 つの数値だけを調整してください：
> `0.15` ≈ ハロー全体の幅 12px（カーソルに密着）／`0.2`（デフォルト）≈ 15px／`0.3` ≈ 21px／`0.6`（原本の値）≈ 40px。

## 実装の詳細（参考）

### 1. マウントポイント：`contentComponent` にしか取り付けられない

これは本プロジェクトの**最も重要な結論**です。

実測により、`editor.getContentComponent()`（実際の型は `EditorComponentImpl`）が**唯一安全なマウントポイント**であることが分かりました：

| 特性 | なぜ重要か |
|---|---|
| `JTextComponent` であり、**`layout` が `null`** | `LayoutManager` が存在しないため、`revalidate()` の際に再レイアウトしてオーバーレイを引き伸ばすことがない |
| 座標系が `visualPositionToXY()` と**自然に一致** | 座標変換がまったく不要 |

**試したうえで否定されたマウントポイント**（いずれもオーバーレイがエディタ全体まで引き伸ばされ、「画面全体の色が変わる」現象になります）：

- `contentComponent.getParent()`（`JBViewport`）
- `editor.getComponent()`（エディタパネル）
- 祖先の `JLayeredPane`（コミュニティの手法として挙げられているもの。実測では確かに存在します —— `EditorImpl$PanelWithFloatingToolbar` —— が、**この目的には使えません**）
- ウィンドウルートの `LayeredPane`

### 2. トレイルの原理：残像ではなく「引き伸ばし」

原本（および本プロジェクト）の中核機構は、**残像を何枚も重ねること**ではなく：

1. カーソル矩形には **4 つの角点**があり、各角点に X/Y の減衰バネを 1 組ずつ取り付ける
2. カーソルが移動すると、「運動方向と角点方向のなす角」に応じて四隅を**ランク付け**する（`assignRanks`）
3. 運動の**前方**にある角は大きな係数を得て（ぴったり追従し、ハードスナップすることもある）、**後方**の角は小さな係数を得る（遅れてついてくる）
4. その結果、矩形が**不規則な四角形に引き伸ばされる** —— 視覚的にはこれがトレイルです

この設計は残像方式より軽量です（4 点だけで済みます）が、**1 フレーム単位の補間精度に厳しい要求があり**、低フレームレートでは問題が表面化します（後述）。

### 3. 残像モデルの実装ポイント

残像モデルはバネモデルより単純に見えます（位置を記録して描くだけ）が、**やらなければまったく成立しない** 2 つの細部があります：

**(a) サンプル点の間に補間点を挿入する必要がある**

低フレームレートでは 1 フレームの移動量が大きく（20fps では 1 回のジャンプが 200px 以上に及ぶこともあります）、
サンプルの端点だけを記録すると、数十～数百ピクセル離れた**孤立したブロック**がいくつか並ぶだけになります ——
見た目は「カーソルが飛んでいる」だけで、トレイルにはなりません。

一定間隔（`MAX_GAP_PX = 5`）で点を補って初めて、軌跡が連続になります。
**タイムスタンプも同時に補間する必要があります**。そうしないと補った点が同じ明るさになり、「硬いブロックの連なり」になってしまいます。

**(b) 常駐カーソルを別途 1 つ描画する必要がある**

残像には寿命（`lifetime`）があり、期限が来ると破棄されます ——
**カーソルがしばらく静止すると残像がすべてフェードアウトし、画面が空になります**。
そのため毎フレーム、現在位置に alpha が常に 1 の「カーソル本体」も描画する必要があります。
（末尾を描画する際は、現在位置と重なるサンプル点をスキップしてください。そうしないと両者が重なり、その部分の色が濃くなります。）

> バネモデルにはこの問題がありません。4 つの角点は常に目標位置に留まります。

### 4. グローのシミュレーション：多層の同心外拡

Canvas の `shadowBlur` は本物のガウスぼかしであり、Swing に等価なものはありません。本プロジェクトの近似方法は
**多層の同心外拡 + 塗りつぶし**です：最も外側の層（外拡量が最大）から内側へ向かって 1 層ずつ描画し、
層と層の間は SrcOver が自然に累算されるため、「内側が明るく外側が暗い」連続的なグラデーションが得られます。

**各層の alpha は層数から逆算します**。各層の独立した不透明度を A とすると、N 層を重ねたときの最も内側の累積は
`1 - (1-A)^N` になります。これをちょうど `glowOpacity` に等しいと置くと、

```
A = 1 - (1 - peak)^(1/N)
```

こうすることで「層数」と「強度」という 2 つのパラメータが互いに干渉しません ——
層数を増やしても遷移がより滑らかになるだけで、**ハロー全体が明るくなることはありません**。

**半径は線形に分布させます**。半径 r における累積不透明度は `1-(1-A)^k` で、k はその点を覆う層数です。
半径が線形分布なら k も線形になり、`r ≈ glowWidth/2` の地点でちょうどピークの約 60% まで減衰する計算になります。
ガウス曲線とよく一致します。

**ハローは四角形そのものに密着させる必要があります**。この点は 3 回試行錯誤しました（落とし穴 #12 → #13 → #14 に対応）：

| 試行 | 失敗した理由 |
|---|---|
| 多層の**中央ストローク** | ストロークのパスは矩形の内部ではなく境界線であり、最も明るい層は外側に 1px 未満しか広がらず、しかも不透明な本体に覆われてしまう |
| **バウンディングボックス**を形状に使う | トレイル時には四隅が細長い斜めの帯に引き伸ばされるのに、バウンディングボックスはエディタの大半を覆ってしまう → 行をまたぐジャンプで大きな正方形に膨らむ |
| **正確な外拡**（最終採用） | 各辺を外法線方向に平行移動し、隣接する辺の交点を求める。鋭角では √2 でクランプしないと、長い棘が飛び出す |

**グローは運動時にだけ点灯します**：強度は四隅の目標値からの最大オフセットで駆動されます ——
静止時はオフセットが 0 なので描画を完全にスキップし、実際に移動したときのオフセットは最小でも 1 文字幅（約 8px）
または 1 行の高さ（約 32px）になります。したがって 2.5px をフル強度のしきい値にすれば、**移動時の見え方にまったく影響しません**。
詳細は落とし穴 #16 を参照。

### 5. ネイティブカーソルの非表示

IntelliJ にはカーソルを非表示にする公開 API が**ありません** —— `Editor` / `CaretModel` / `Caret` の 3 つのインターフェースは
すべて `javap` による逆コンパイルで確認済みです（`Editor` は `getColorsScheme()` を提供するだけで setter がなく、
したがって「特定のエディタだけ非表示にする」方法も存在しません）。

唯一実行可能な方法は、**グローバルカラースキーム**を変更することです：

```java
EditorColorsManager.getInstance().getGlobalScheme()
        .setColor(EditorColors.CARET_COLOR, new Color(0, 0, 0, 0));
```

⚠️ **この操作はグローバルであり、代償は自分で引き受ける必要があります**：一度非表示にすると、IDE 内の**すべての**エディタのネイティブカーソル
が消えます —— 我々が引き継ぐつもりのないもの（Build / Run / Services などの出力エリア）も含めて。
**非表示にしたものにはすべて、代替カーソルを我々が描き足さなければなりません**。そうしないと、それらの位置のカーソルは完全に消えてしまいます。
詳細は落とし穴 #8 を参照。

**⚠️ 直感に反する永続化の経路**：`setColor` 自体は確かにメモリを変更するだけで設定ファイルには書き込みませんが、
**メモリ上の状態は IDE によって間接的にディスクへ書き出されます** —— ユーザーが Settings でエディタ設定をどれか 1 つでも変更し
OK をクリックすれば、IntelliJ は現在のカラースキームを**丸ごと**保存し、透明カーソルが
`colors/_@user_<スキーム名>.icls` に書き込まれます。以後は**プラグインをアンインストールしても自己修復しません**。壊れた値がすでにディスク上に存在するからです。

本プラグインではこれに対する防御を追加しています：`sanitizeCaretColor()` は「完全透明」を元の値として保存することを拒否し、
プラグインをオフにする際はエディタのデフォルト前景色で復元します。詳細は落とし穴 #18 を参照。

### 6. 高精度スケジューリング：`javax.swing.Timer` を使わない

実測データ（Windows 11 + JDK 21）：

| タイマー機構 | 実測精度 |
|---|---|
| `javax.swing.Timer`（内部は `Object.wait`） | **15.61 ms** ❌ |
| `LockSupport.parkNanos` | 15.35 ms ❌ |
| **`Thread.sleep`** | **1.56 ms** ✅ |
| システムクロックの粒度 | 1.08 ms |

システムクロック自体は高精度ですが、`Swing Timer` が使う `Object.wait` ではそれを引き出せません —— フレームレートは **64fps** に固定されてしまいます。

そのため、**バックグラウンドスレッドの `Thread.sleep` でスケジューリングし、`invokeLater` で EDT に戻して描画する**方式に変更しました。

## 落とし穴の記録

> 以下はすべて実測で踏んだものです。後から来る人の参考になれば幸いです。

### #1 `container.revalidate()` を呼んではいけない

`LayoutManager` を持つコンテナに対して `revalidate()` を呼ぶと、レイアウトマネージャが**すべての**子コンポーネントを再レイアウトし、オーバーレイが 10×24 からエディタ全体まで引き伸ばされます → **画面全体の色が変わる**。

**`repaint()` だけを使うこと。**

### #2 `paintComponent` で背景を描いてはいけない

オーバーレイは多角形だけを描き、**矩形の背景は決して描きません**。こうしておけば、万一引き伸ばされても多角形自体しか表示されません。

### #3 `paintImmediately` を使ってはいけない（重要）

「EDT のスケジューリング遅延を減らす」ために `repaint` を `paintImmediately` に変えたところ、**性能はむしろ大幅に低下**しました：

| バージョン | ピーク fps |
|---|---|
| `repaint`（非同期） | **105.6** |
| `paintImmediately`（同期） | **36.9** |

原因：`paintImmediately` は自分の領域を同期的に描画するだけでなく、**`RepaintManager` にキューイングされたすべてのダーティリージョンをまとめて処理してしまいます** —— テキスト削除などの操作で大量のダーティリージョンが発生すると、EDT が長時間ブロックされます。

**`repaint` の「非同期」は欠陥ではなく、`RepaintManager` に統合と最適化の機会を与えるものです。**

### #4 バネの減衰係数 `c` を変更してはいけない

バネの更新式において、`c` は単なる減衰係数ではなく、**速度の積分にも関与します**：

```java
position = (a + b * dt) * c;    // b には「速度による変位」がすでに含まれている
```

低フレームレートの見え方を改善しようと `c` に下限を設けたところ、位置が**逆に増幅**されました：

```
正常：c=0.135 → (100 + 4000×0.05) × 0.135 = 40.5   ✓ 減衰
改悪：c=0.5   → (100 + 4000×0.05) × 0.5   = 150    ✗ 1.5 倍に増幅！
```

フレームごとに累積すると、アニメーションは**破綻**します。

**1 フレームあたりの変位を制限するには、計算結果を出した後に `position` の変化量を制限しなければなりません。**

### #5 `caretPositionChanged` のタイミングに依存してはいけない

テキスト削除などの場面では、カーソルイベントが `visualPositionToXY()` のデータ更新**より前に**発火することがあります —— この場合、古い位置を読んでしまい、その後新しいイベントは来ないため、トレイルが**永久に古い位置に留まります**。

**正しい方法**：毎ティックごとにカーソル位置を読み直し、イベントは「高フレームレートへの起床」にのみ使います。同時に軽量な `getVisualPosition()` でファストパスを設け、毎フレーム高コストな座標変換を行わないようにします。

### #6 トレイルの最大長は厳しく絞るべき

原本の JS は `maxTrailDistanceFactor = 60`（約 1920px）で、Canvas の全画面再描画では問題ありません。

しかし Swing のオーバーレイは**部分再描画**が必須です —— トレイルが長いほど再描画が必要なバウンディングボックスが大きくなり、行をまたぐジャンプではほぼ全画面の再描画に退化します。

**4（約 128px）まで絞ったところ、通常の移動にはまったく影響しません。**

### #7 再描画領域は個別に提出し、union してはいけない

「前フレームの領域」と「現フレームの領域」を 1 つの大きな矩形に union してから再描画すると、行をまたぐジャンプでエディタの大半を覆ってしまいます。

**`repaint` を 2 回に分けて提出すること。**

### #8 コンソールエディタ：一律にフィルタリングもできず、一律に引き継ぎもできない

これは前後で 2 回間違えました。結論を完全に記録します。

**1 回目の誤り**：`EditorKind.CONSOLE` で一律にフィルタリングしていた。理由は「ターミナルはカーソルを自前で描画するので、
マウントすると追従しない偽カーソルが増えるだけ」。**この理由はターミナルには当てはまりますが、出力コンソールには当てはまりません** ——
Build / Run / Services / Problems の出力エリアも `CONSOLE` ですが、
それらのカーソルは**まさに `CARET_COLOR` に制御されています**。グローバル非表示 + 一律フィルタリング
= それらの位置のカーソルがすべて消えます。

**2 回目の誤り**：フィルタリングできないなら、すべての `CONSOLE` にカーソルを描き足せばよいと考えた。
結果、**ターミナルが二重カーソルになりました** —— ターミナル自身のカーソルはもともと非表示になっていないのに、もう 1 つ描き足したためで、
しかも位置も同期しません（我々は Editor の caret を読むが、ターミナルの実際のカーソルはエミュレータが管理しており、実測で 1 文字ずれていました）。

**正しい方法：2 種類を分けて扱う。**

| エディタ | カーソルの由来 | 扱い |
|---|---|---|
| コードエディタ（`MAIN_EDITOR`） | `CARET_COLOR` | 非表示 + トレイル |
| 出力コンソール（`CONSOLE`） | `CARET_COLOR` | **静的カーソルを描き足す**（トレイルなし） |
| ターミナル（`CONSOLE`） | ターミナルエミュレータが自前で描画 | **スキップ**し、何もしない |

**難しいのは後ろ 2 つの型が完全に同じことです**：`TerminalEditorFactory.createOutputEditor()`
が返すのは標準の `EditorImpl` で、両者の `EditorKind` も `CONSOLE` なので、型では区別できません。
最終的に**コンポーネントツリーを上方向にたどり**、terminal のパッケージ名にヒットしたらターミナルと判定する方式にしました：

```java
Component c = editor.getContentComponent();
while (c != null) {
    String name = c.getClass().getName();
    if (name.startsWith("com.intellij.terminal")
            || name.startsWith("org.jetbrains.plugins.terminal")) {
        return true;   // ターミナル、スキップ
    }
    c = c.getParent();
}
```

具体的なクラス名ではなく**パッケージ名のプレフィックス**を使うのは、ターミナルがここ数バージョンで実装を変えているためです
（`org.jetbrains.plugins.terminal` → `com.intellij.terminal.frontend`）。一方、パッケージ名は常に安定しています。

> **教訓**：ある操作が**グローバルな副作用**を伴う場合、「ある種のオブジェクトをスキップする」ことと
> 「ある種のオブジェクトを素通しする」ことはまったく別の話です。フィルタ条件は、副作用の**実際の作用範囲**に立ち返って確認すべきであり、
> 「この種のオブジェクト自身が処理を必要とするか」だけで判断してはいけません。

### #9 残像には補間点が必須。でないと「カーソルが飛んでいる」だけになる

前述の「残像モデルの実装ポイント」の (a) を参照。これが初版の残像モードが完全に機能しなかった原因です ——
低フレームレートでは数百ピクセル離れたサンプル点が数個しかなく、視覚的にはカーソルが飛んでいるだけでした。

### #10 残像モードでは常駐カーソルを別途描画する必要がある

前述の「残像モデルの実装ポイント」の (b) を参照。バネモデルから移植する際に最も見落としやすい差異です ——
バネの角点は常に目標位置に留まりますが、残像は時間とともにフェードするため、しばらく静止すると画面が空になります。

### #11 トレイルの最大長は「視覚効果」ではなく「再描画コスト」で決める

前述の #6 を参照。補足として：**行をまたぐジャンプが最も過酷なシナリオです** ——
「トレイルの伸長」と「再描画面積」の 2 つの要素を同時に増幅します。
パラメータ調整時はこれで検証すべきで、同行内の移動だけでテストしてはいけません。

### #12 グローは「中央ストローク」では実装できない

`BasicStroke` のストロークパスは矩形の**境界線**であり内部ではないため、各層は外側に `strokeWidth/2` しか広がりません。

IntelliJ のカーソルは極端に細いため（2×32）、最も明るい層（strokeWidth が最小）は外側に 1px 未満しか広がらず、
直後に塗りつぶされる不透明な本体に覆われてしまいます。一方、十分に広がる層は alpha がすでに 2% 以下に減衰しています。

**結果は「ぼかしはあるが発光がない」** —— これこそが当初「バネモードでグローが感じられない」の根本原因でした。

**正しい方法**：ストロークではなく、多層の同心**外拡**（塗りつぶし）にすること。

### #13 ハローの形状にバウンディングボックスは使えない

外拡に切り替えた後、手を抜いて `polygon.getBounds()` をハローの形状に使ってしまいました。理由は
「ハロー自体がぼやけているのだから、バウンディングボックスの誤差は見えないはず」。

**この判断は完全に間違っていました。** トレイル時には 4 つの角点が斜めの細長い四角形に引き伸ばされる一方、
その**バウンディングボックス**はエディタの大半を覆い得ます —— 行をまたぐジャンプの瞬間、
ハローはまず巨大な正方形に膨らみ、その後四角形の収縮に合わせて縮みます。「トレイルに密着して発光する」とは程遠い挙動です。

**教訓**：形状の近似に関しては、**最悪ケース**（行をまたぐジャンプ）を検証すべきで、静止状態だけを見てはいけません。

### #14 正確な外拡は鋭角で制御を失う

多角形外拡の厳密解では、角点のオフセット量 ∝ `1/cos(θ/2)` —— なす角が小さいほど交点が遠くなります。

トレイル時には四角形が細長い帯に引き伸ばされ、**前後の端がまさに鋭角**になります。実測ではオフセットが目標値の **2.4 倍**に達し、
ハローが両端から長い棘となって飛び出しました。

**修正**：オフセットベクトルのノルムを `√2` にクランプする。直交部分（静止した矩形）のオフセットはちょうど √2 なので
影響を受けず、鋭角部は妥当な範囲に押し戻されます —— これは実際のガウスぼかしが鋭角を「丸める」挙動にもより近くなります。

> この修正の正しさは `tools/OffsetTest.java` による独立検証で確認済みです ——
> 検証項目：静止した矩形の外拡量が正確、中心のドリフトがゼロ、鋭角が √2 でクランプされる、外拡後も凸四角形のまま。
> 使い方：`javac -encoding UTF-8 tools/OffsetTest.java && java OffsetTest`

### #15 グローのサイズに原本の `shadowBlurFactor` をそのまま使ってはいけない

原本の `shadowBlurFactor = 0.6` が記述しているのは Canvas の `shadowBlur`、すなわちガウスぼかしの**直径**です。

ぼかしはエネルギーを広げるため、**図形が細いほどピークが薄まります**：VS Code のカーソルは 8px 幅あり、
まだ持ちこたえられますが、IntelliJ のカーソルは 2px 幅しかありません。同じ数値をそのまま外拡半径として使うと、
幅約 40px の楕円形の霧（カーソル幅の 20 倍）になり、「カーソルに密着して発光する」とは到底言えません。

**修正**：`0.2` まで下げ、ハロー全体の幅を約 15px にしました。

> これは本プロジェクトが**意図的に原本のパラメータから逸脱している唯一の箇所**です。あの誇張された広範囲の光の霧を再現したい場合は、
> `0.6` に戻してください。

### #16 静止したカーソルにグローは不要

グローは「運動中」にこそあるべき効果です。カーソルが静止しているのに周囲が光っていると、ピンクの四角形に囲まれているように見えます。

**方法**：四隅の目標からの最大オフセット量（＝トレイルの展開度合い）でグローの強度を駆動します ——
オフセット ≤ 0.5px は静止とみなして描画を完全にスキップし、≥ 2.5px でフル強度とします。

遷移領域を 2px 幅しか取らないのは、この 2 つの状態がもともと大きく離れているためです：
静止時のオフセットは 0 であり、実際に移動したときのオフセットは最小でも 1 文字幅（約 8px）か 1 行の高さ（約 32px）になります。
**この狭い区間が、移動時のグローを変更前とピクセル単位で一致させつつ、停止時の消灯を柔らかにしています。**

### #17 `untilBuild` を固定してはいけない。さもないとプラグインが「1 つの IDE バージョンでしか使えない」ものになる

初期バージョンの `build.gradle.kts` にはこう書かれていました：

```kotlin
ideaVersion {
    sinceBuild.set("252")
    untilBuild.set("252.*")     // ← 元凶
}
```

結果、プラグインは**2025.2 でしか使えませんでした** —— 2024.x、2025.1、2025.3、2026.x はすべて IDE に拒否され、
ユーザーに見えるのは「プラグインが現在の IDE と互換性がありません」の一言だけで、原因はまったく分かりません。

**機構**：IDE は起動時に `build.txt` の build 番号を取得し、プラグインの
`since-build` / `until-build` の範囲と比較して、範囲外なら**読み込みを直接拒否**します。
コードの実行段階にすら到達しません。つまりこれは**API の互換性問題ではなく、メタデータ宣言の問題**です ——
1 語の設定が「プラグインは 1 バージョンしかサポートしない」と等価な効果を持ちます。

**正しい方法**：プラグインがバージョン固有のコードを含まないなら、**`untilBuild` を省略する**（空欄はすべての新しいバージョンに適用されることを意味します）。
これは JetBrains 公式の推奨です。

**自分が「バージョン固有のコードを含むか」を判断する方法**：依存する API がすべてプラットフォームの中核インターフェースかどうかを見ます。
本プラグインが使っているのは `Editor` / `CaretListener` / `EditorColors` / `EditorFactoryListener` などで、
その中で「最も若い」`EditorKind` も 2016.2 に導入されたものです —— このような場合は上限を設けなくて構いません。

| 書き方 | 結果 |
|---|---|
| `untilBuild` を固定 | IDE をアップグレードするたびに再リリースが必要で、ユーザーはそれまで使えない |
| `untilBuild` を省略 | 1 回の設定が長期間有効。本当に breaking change が来たときに絞ればよい |

**下限は必ず実測が必要です**：`sinceBuild` は感覚で緩めてはいけません。API の差異に加えて、**バイトコードのバージョン**にも注意が必要です ——
本件では 2024.1 は API が存在しないのではなく、JBR 17 が Java 21 のバイトコードを読み込めない点でつまずいています。

### #18 「メモリだけの変更」は「ディスクに残らない」ではない —— カラースキームが静かに汚染される

ネイティブカーソルを非表示にするには、グローバルカラースキームの `CARET_COLOR` を変更するしかありません。ここで**思い込みの推論**がありました：

> `setColor()` はメモリ上のオブジェクトを変更するだけでファイルには書き込まない → プラグインが異常終了しても痕跡は残らない → リスクは制御可能。

前半は正しいですが、**後半は誤りです**。実際に起きた連鎖：

```
① プラグインがメモリ上の CARET_COLOR を完全透明に変更する
        ↓
② ユーザーが Settings でエディタ設定をどれか 1 つ変更し（本例はフォント）、OK をクリック
        ↓
③ IntelliJ がカラースキームを保存する際、【その時点のメモリ状態】を丸ごとディスクへ書き出す
   → colors/_@user_Dark.icls に 1 行増える：
      <option name="CARET_COLOR" value="00000000" />
        ↓
④ 以後はプラグインのインストール有無にかかわらず、カーソルは見えないまま —— 壊れた値はすでにディスク上にある
```

**なぜ気づきにくいか**：「プラグインが動作中」と「ユーザーが OK を押した」の 2 つが同時に起きる必要があるためです。しかも
`partialSave="true"` のスキームファイルは親スキームとの**差分項目**しか記録しないので、その 1 行は通常のフォント設定に紛れて、
目で追っても異常に気づけません。本例ではそのファイルの唯一の色差分項目が `CARET_COLOR` でした —— これこそが決定的な証拠です：
ユーザーはフォントしか変更していないのに、カーソル色が「ついでに」書き込まれているのです。

**なぜ特に危険か**：**プラグインをアンインストールしても自己修復しません**。ユーザーが遭遇する現象は
「プラグインを入れていないのにカーソルが見えない」であり、調査の方向が IDE 本体へと完全に逸れてしまいます。

**修正**：その行を削除し、スキームを親スキームの値にフォールバックさせます：

```xml
<scheme name="_@user_Dark" version="142" parent_scheme="Darcula">
  <colors>
    <option name="CARET_COLOR" value="00000000" />   <!-- ← この行を削除 -->
  </colors>
</scheme>
```

IDE のバージョンごとに 1 つずつ存在するため（`IntelliJIdea2025.2` / `IntelliJIdea2026.2` / …）、**すべて修正する必要があります**。
修正前に IDE を終了してください。そうしないと終了時にメモリ上の状態で上書きされてしまいます。

**プラグイン側の防御**：`sanitizeCaretColor()` —— 完全透明（または `null`）を読み取った場合、それを「元の値」として保存しません。
なぜなら、そうすると「復元」が透明をそのまま返すことと等価になるからです。代わりに `getDefaultForeground()` でフォールバックし、
ユーザーが少なくともカーソルを見られるようにしています。

| 書き方 | プラグインをオフにした後 |
|---|---|
| `savedCaretColor = scheme.getColor(...)` | 透明に復元 —— **カーソルは依然として現れない** |
| 先に `sanitizeCaretColor()` でフィルタ | デフォルトの前景色に復元 —— カーソルは正常 |

**教訓**：「変更が永続化されるか」を判断する際は、**自分がファイルを書いたかどうか**だけでなく、
**このオブジェクトに他のディスク書き出し経路がないか**も見る必要があります。メモリ上のグローバルシングルトンは、IDE 自身の保存動作にいつでも持ち去られる可能性があります。

## 既知の制限

### フレームレートの上限

**これが本プロジェクトの最も核心的な未解決問題です。**

実測フレームレートは **20~50fps** の間で変動します（ピークは 105fps）。

**根本原因は描画ではありません**。決定的な実験を行いました —— スイッチを追加して**描画をすべてスキップ**し、物理計算だけを実行します：

```
fps=10.9   （再描画は完全にスキップ済み）
fps=4.1
fps=4.0
fps=2.0
fps=0.4
```

**まったく描画しなくても、フレームレートは依然として 2~43 しか出ません** —— ボトルネックが **EDT のスケジューリング**にあり、描画とは無関係であることの証明です。

**機構**：AWT の `EventQueue` では、**ネイティブ入力イベント（キーボード/マウス）の優先度が `invokeLater` で投入されたタスクより高い**です。カーソルを素早く移動させると、キーボードイベントとエディタ自身の再描画が EDT を埋め尽くし、我々の描画タスクは後ろに並ぶしかありません。

これがあの直感に反する現象、**「エディタ自体はカクつかないのに、カーソルだけがカクつく」**の説明にもなります。

### もう 1 つの直感に反する現象

**大きくジャンプするほうが、隣接する 2 行の移動より滑らかに感じられます。**

理由は 2 層あります：

1. **視覚的な錯覚**：同じフレーム数なら、変位が大きいほど 1 フレームあたりの視覚的変化が大きく、カクつきに気づきにくい
2. **アルゴリズム層**：低フレームレートでは `dt` が大きく、短距離アニメーションの時間はそれに近いため、`DampedSpring.update()` の冒頭のショートサーキット条件 `animationLength <= dt` に**丸ごと飲み込まれる** —— カーソルはアニメーションなしで瞬時に目標へ飛ぶ

2 点目は**低フレームレート向けアニメーション補償**（少なくとも 6 フレームを跨ぐことを保証）で修正済みです。

## クレジット

- **原案の効果**：Neovide（[neovide.dev](https://neovide.dev/)）
- **アルゴリズムの原型**：VS Code 版 `neovide-cursor.js` —— 本プロジェクトの `DampedSpring` / `TrailCorner` はそこから行単位で移植したものです
- **コミュニティの参考**：`intellij-smooth-caret`（スムーズカーソル）、JetBrains 公式 2026.1 の Smooth Caret（Snappy / Gliding）

> 補足：JetBrains 公式およびコミュニティプラグインの「スムーズカーソル」は、**どちらもスムーズな移動のみでトレイルがありません**。したがって本プロジェクトは適応ではなく独立した実装です。
