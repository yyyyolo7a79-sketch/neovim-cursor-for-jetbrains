## 效果

游標移動時：

- **拖尾**：游標被「拉長」成不規則四邊形（彈簧模型）
- **平滑跟隨**：阻尼彈簧驅動，非瞬時跳變
- **輝光**：邊緣柔和光暈（模擬 Canvas `shadowBlur`），**隨拖尾展開而亮起、游標靜止時自動熄滅**
- **原生游標隱藏**：避免與拖尾重疊

參數語義與 VS Code 版 `neovide-cursor` 對齊，便於跨平台移轉設定（唯一例外見[參數設定](#參數設定)）。

### 兩種拖尾模型（可在選單中隨時切換）

| 模式 | 原理 | 特點 |
|---|---|---|
| **彈簧**（預設） | 游標矩形的四個角點各掛一組阻尼彈簧，按運動方向分配不同滯後係數 → 矩形被拉伸 | Neovide 原版效果；依賴幀間內插 |
| **殘影** | 記錄游標每一幀的真實位置，繪製一串漸隱殘影 | **掉幀不失真**，低幀率下更穩定；輝光觀感比彈簧模式更明顯 |

兩者共用同一套基礎設施（覆蓋層掛載、原生游標隱藏、高精度排程、局部重繪），
只有「位置計算」部分不同。

## 安裝

### 方式一：從 Release 下載（推薦）

1. 到 [Releases](https://github.com/yyyyolo7a79-sketch/neovim-cursor-for-jetbrains/releases) 下載最新的 `*.zip`
2. IDEA → `Settings` → `Plugins` → `⚙️` → `Install Plugin from Disk...`
3. 選擇該 zip，重新啟動 IDE

### 方式二：自行建置

```bash
# 要求：JDK 21、Gradle 9.0+、IntelliJ Platform Gradle Plugin 2.x
./gradlew buildPlugin
# 產物：build/distributions/*.zip
```

若使用本機已安裝的 IDE（免下載數 GB 的發行包），在 `build.gradle.kts` 中改：

```kotlin
dependencies {
    intellijPlatform {
        local("D:/path/to/IntelliJIdea2025.2")   // 換成你的安裝路徑
    }
}
```

## 相容性

**支援範圍：2024.2 ~ 2026.2 及以上**

| IDE | 版本 | 狀態 |
|---|---|---|
| IntelliJ IDEA | 2024.2 – 2026.2 | ✅ 實測通過 |
| CLion | 2025.2 | ✅ 實測通過 |
| PyCharm | 2025.2 | ✅ 實測通過 |

**為什麼能跨 IDE 通用**：外掛只依賴 `com.intellij.modules.platform`
（平台核心模組），不涉及任何語言特有的 API，也不依賴 IDEA Ultimate 的專有功能。
因此適用於所有 2024.2+ 的 JetBrains IDE ——
WebStorm / PhpStorm / GoLand / RubyMine / Rider / DataGrip 等。

### 版本下限為什麼是 2024.2

2024.2 是平台改用 **JBR 21** 的起點，與本外掛的編譯目標（Java 21）一致。
2024.1 及更早版本執行於 **JBR 17** 上，載入 Java 21 位元組碼會直接拋出
`UnsupportedClassVersionError` 崩潰 —— 這是位元組碼層面的硬性限制，與 API 無關。

### 版本上限為什麼不設

`<idea-version since-build="242" />` 中**刻意省略了 `until-build`**。
外掛不含任何版本特定程式碼，對後續版本天生相容，因此留空表示「適用於所有更新版本」。

> 這是 JetBrains 官方推薦的寫法。寫死上限（如曾經的 `252.*`）會導致
> **每次 IDE 升級外掛都被判為「不相容」**，使用者只能等新版本發布 ——
> 本外掛早期版本正是栽在這裡，詳見踩雷 #17。

### 想支援更早的版本？

需要把編譯目標降到目標平台內建的 JBR 版本：

| IDE 版本 | build | 內建 JBR | 所需編譯目標 |
|---|---|---|---|
| 2022.x | 221–223 | 11 | Java 11 |
| 2023.x | 231–233 | 17 | Java 17 |
| 2024.1 | 241 | 17 | Java 17 |
| **2024.2+** | **242+** | **21** | **Java 21（目前）** |

好消息是**低版本位元組碼能被高版本 JBR 載入** ——
降低編譯目標不會影響現已支援的 2024.2~2026.2，屬於純擴充。

## 使用

- **開關**：`Tools` 選單 → `Neovide 拖尾光标（开关）`
- **切換拖尾模型**：`Tools` 選單 → `Neovide 光标：残影模式（低帧率更稳）`
  - **勾選** = 殘影模式；**取消勾選** = 彈簧模式（Neovide 原版效果）
  - **即時生效**，無需重新啟動 IDE
- **效能診斷**：`Tools` 選單 → `Neovide 光标：性能诊断（禁用重绘）`
  - 勾選後跳過全部繪製，只跑物理計算。用於區分「繪製慢」還是「排程慢」——**這是個很有用的排查手段**

關閉開關會立即恢復原生游標並移除覆蓋層。

## 參數設定

全部參數在 `core/NeovideConfig.java`，命名與語義均對齊 VS Code 版 `neovide-cursor.js` 的 `cursorConfig`：

| 參數 | 預設值 | 說明 |
|---|---|---|
| `tailColor` | `#FFC0CB` | 拖尾顏色 |
| `useShadow` / `shadowColor` | `true` / `#FFC0CB` | 輝光開關與顏色 |
| `shadowBlurFactor` | `0.2` | 輝光外擴半徑 = 該係數 × 游標較長邊（**已偏離原版 0.6，原因見踩雷 #15**） |
| `animationLength` | `0.1` | 一般動畫時長（秒），越大拖尾越長 |
| `shortAnimationLength` | `0.05` | 短距離移動的動畫時長 |
| `shortMoveThreshold` | `8` | 短距離判定閾值 |
| `trailFactors` | `1 / 0.9 / 0.5 / 0.3` | 四角滯後係數（拖尾拉伸的核心） |
| `useHardSnap` / `leadingSnapThreshold` | `true` / `0.5` | 前緣角硬吸附 |
| `maxTrailDistanceFactor` | `60` | 拖尾最大長度係數，與原版一致（見踩雷 #6） |
| `glowLayers` / `glowOpacity` | `12` / `0.55` | 輝光的層數與峰值強度（**層數不影響亮度**，見下文「輝光的模擬」） |

> 除 `shadowBlurFactor` 外，本表與原版 `cursorConfig` **逐項一致**。
> 若您覺得光暈偏大或偏小，只需調 `shadowBlurFactor` 一個數值：
> `0.15` ≈ 光暈總寬 12px（貼著游標）／`0.2` 預設 ≈ 15px／`0.3` ≈ 21px／`0.6` 原版數值 ≈ 40px。

## 技術實作（供參考）

### 1. 掛載點：只能掛在 `contentComponent` 上

這是本專案**最重要的結論**。

實測顯示，`editor.getContentComponent()`（實際型別 `EditorComponentImpl`）是**唯一安全的掛載點**：

| 特性 | 為什麼關鍵 |
|---|---|
| 它是 `JTextComponent`，**`layout` 為 `null`** | 沒有 `LayoutManager` 會在 `revalidate()` 時重新佈局並拉伸覆蓋層 |
| 座標系與 `visualPositionToXY()` **天生對齊** | 完全不需要座標轉換 |

**曾經嘗試並已證偽的掛載點**（都會導致覆蓋層被拉伸到整個編輯器、表現為「全螢幕變色」）：

- `contentComponent.getParent()`（`JBViewport`）
- `editor.getComponent()`（編輯器面板）
- 祖先 `JLayeredPane`（社群方案所稱，實測它確實存在——`EditorImpl$PanelWithFloatingToolbar`——但**不能用於此目的**）
- 視窗根 `LayeredPane`

### 2. 拖尾原理：拉伸，不是殘影

原版（以及本專案）的核心機制**不是疊加多張殘影**，而是：

1. 游標矩形有 **4 個角點**，每個角點各掛一組 X/Y 阻尼彈簧
2. 游標移動時，按「運動方向與角點方向的夾角」給四角**排序**（`assignRanks`）
3. 位於運動**前方**的角拿到大係數（跟得緊，甚至硬吸附），**後方**的角拿到小係數（拖沓）
4. 於是矩形被**拉長成不規則四邊形** —— 視覺上就是拖尾

這個設計比殘影方案更精簡（只需 4 個點），但**對單幀內插精度要求高**，在低幀率下會暴露問題（見下文）。

### 3. 殘影模型的實作要點

殘影模型看似比彈簧模型簡單（記錄位置 + 畫出來），但有兩個**不做就完全不成立**的細節：

**(a) 必須在取樣點之間補內插點**

低幀率下每幀位移很大（20fps 時一次跳轉可能跨 200px+），
若只記錄取樣端點，得到的會是幾個相距數十上百像素的**孤立方塊** ——
看起來就是「游標在跳」，完全沒有拖尾。

按固定間距（`MAX_GAP_PX = 5`）補點後，軌跡才是連續的。
**時間戳記也要同步內插**，否則補出來的點會等亮度，形成「一串生硬的方塊」。

**(b) 必須額外畫一個常駐游標**

殘影有壽命（`lifetime`），到期即被淘汰 ——
**游標靜止一會兒後所有殘影淡出，畫面就空了**。
因此每幀還要在當前位置畫一個 alpha 恆為 1 的「游標本體」。
（繪製尾巴時要跳過與當前位置重合的取樣點，否則兩者疊加會讓該處顏色偏深。）

> 彈簧模型沒有這個問題：四個角點永遠停在目標位置。

### 4. 輝光的模擬：多層同心外擴

Canvas 的 `shadowBlur` 是真正的高斯模糊，Swing 沒有等價物。本專案的逼近方式是
**多層同心外擴 + 填滿**：從最外層（外擴量最大）逐層向內繪製，
層與層之間由 SrcOver 自然累加，於是形成「內亮外暗」的連續漸層。

**每層 alpha 由層數反解**。設每層獨立不透明度為 A，N 層疊加後最內層的累積為
`1 - (1-A)^N`；令它恰好等於 `glowOpacity`，即

```
A = 1 - (1 - peak)^(1/N)
```

這樣「層數」與「強度」兩個參數互不干擾 —— 加層數只會讓過渡更細膩，
**不會讓光暈整體變亮**。

**半徑按線性分布**。累積不透明度在半徑 r 處為 `1-(1-A)^k`，k 是覆蓋該點的層數；
半徑線性分布時 k 也線性，算出在 `r ≈ glowWidth/2` 處剛好衰減到峰值的約 60%，
與高斯曲線吻合。

**光暈必須貼著四邊形本身**。這一條試錯了三次（對應踩雷 #12 → #13 → #14）：

| 嘗試 | 失敗原因 |
|---|---|
| 多層**居中描邊** | 描邊路徑是矩形的邊界線而非內部，最亮層只外擴不到 1px 且被不透明主體蓋住 |
| 用**邊界框**做形狀 | 拖尾時四角被拉成細長斜條，邊界框卻能覆蓋大半個編輯器 → 跨行跳轉時撐成大方塊 |
| **精確外擴**（最終採用） | 逐邊外法線平移 + 相鄰邊求交；銳角處需按 √2 截斷，否則甩出長尖刺 |

**輝光只在運動時點亮**：強度由四角相對目標的最大偏移量驅動 ——
靜止時偏移為 0，完全跳過繪製；任何真實移動的偏移至少是一個字元寬（約 8px）
或一行高（約 32px），因此取 2.5px 作為滿強度閾值就能保證**移動時的觀感絲毫不受影響**。
詳見踩雷 #16。

### 5. 隱藏原生游標

IntelliJ **沒有**隱藏游標的公開 API —— `Editor` / `CaretModel` / `Caret` 三個介面
均已用 `javap` 反編譯確認（`Editor` 只提供 `getColorsScheme()`，沒有 setter，
因此也不存在「只隱藏某一個編輯器」的做法）。

唯一可行路徑是改**全域配色方案**：

```java
EditorColorsManager.getInstance().getGlobalScheme()
        .setColor(EditorColors.CARET_COLOR, new Color(0, 0, 0, 0));
```

⚠️ **這個操作是全域的，代價必須自己承擔**：一旦隱藏，IDE 內**所有**編輯器的原生游標
都會消失 —— 包括那些我們並不打算接管的（Build / Run / Services 等輸出區）。
**凡是被隱藏的，都必須由我們補畫一個替代游標**，否則那些位置的游標會徹底消失。
詳見踩雷 #8。

**⚠️ 一個反直覺的持久化路徑**：`setColor` 本身確實只改記憶體、不寫入設定檔，
但**記憶體狀態會被 IDE 間接寫入磁碟** —— 使用者只要在 Settings 裡改過任意一項編輯器設定
並點擊 OK，IntelliJ 就會把當前配色方案**整體**儲存，透明游標隨之寫進
`colors/_@user_<方案名稱>.icls`。此後**解除安裝外掛也無法自癒**，因為壞值已經落在磁碟上了。

本外掛對此加了防護：`sanitizeCaretColor()` 拒絕把「全透明」當作原始值儲存，
關閉外掛時會改用編輯器預設前景色恢復。詳見踩雷 #18。

### 6. 高精度排程：不要用 `javax.swing.Timer`

實測資料（Windows 11 + JDK 21）：

| 計時機制 | 實測精度 |
|---|---|
| `javax.swing.Timer`（內部走 `Object.wait`） | **15.61 ms** ❌ |
| `LockSupport.parkNanos` | 15.35 ms ❌ |
| **`Thread.sleep`** | **1.56 ms** ✅ |
| 系統時鐘粒度 | 1.08 ms |

系統時鐘本身是高精度的，但 `Swing Timer` 用的 `Object.wait` 拿不到 —— 它把幀率釘死在 **64fps**。

因此改為：**背景執行緒 `Thread.sleep` 排程 + `invokeLater` 切回 EDT 繪製**。

## 踩雷紀錄

> 以下每一條都是實測踩出來的，供後人參考。

### #1 不要呼叫 `container.revalidate()`

對帶 `LayoutManager` 的容器，`revalidate()` 會讓佈局管理器重新佈局**所有**子元件，把覆蓋層從 10×24 拉伸到整個編輯器 → **全螢幕變色**。

**只用 `repaint()`。**

### #2 不要在 `paintComponent` 裡繪製背景

覆蓋層只畫多邊形，**絕不畫任何矩形背景**。這樣即使被意外拉伸，也只會顯示多邊形本身。

### #3 不要用 `paintImmediately`（重要）

曾為了「減少 EDT 排程延遲」把 `repaint` 改成 `paintImmediately`，結果**效能反而大幅下降**：

| 版本 | 峰值 fps |
|---|---|
| `repaint`（非同步） | **105.6** |
| `paintImmediately`（同步） | **36.9** |

原因：`paintImmediately` 除了同步繪製本區域，還會**順帶把 `RepaintManager` 中所有排隊的髒區一次性處理掉** —— 刪除文字等操作產生大量髒區時，EDT 被長時間阻塞。

**`repaint` 的「非同步」不是缺陷，而是讓 `RepaintManager` 有機會合併最佳化。**

### #4 不要改彈簧的衰減因子 `c`

彈簧的更新公式中，`c` 不只是衰減係數，**它還參與速度積分**：

```java
position = (a + b * dt) * c;    // b 裡已含「速度帶來的位移」
```

曾試圖給 `c` 設下界來改善低幀率觀感，結果位置被**反向放大**：

```
正常：c=0.135 → (100 + 4000×0.05) × 0.135 = 40.5   ✓ 衰減
改壞：c=0.5   → (100 + 4000×0.05) × 0.5   = 150    ✗ 放大 1.5 倍！
```

逐幀累積後動畫直接**失控**。

**要限制單幀位移，必須在算出結果後限制 `position` 的變化量。**

### #5 不要依賴 `caretPositionChanged` 的時序

刪除文字等情境下，游標事件可能在 `visualPositionToXY()` 資料更新**之前**觸發 —— 此時讀到舊位置，而之後不會再有新事件，拖尾會**永久卡在舊位置**。

**正確做法**：每個 tick 都重新讀取游標位置，事件僅用於「喚醒」到高幀率。同時用輕量的 `getVisualPosition()` 做快速路徑，避免每幀都做耗費成本的座標換算。

### #6 拖尾最大長度要收緊

原版 JS 的 `maxTrailDistanceFactor = 60`（約 1920px），在 Canvas 全螢幕重繪下沒問題。

但 Swing 覆蓋層必須**局部重繪** —— 拖尾越長，需要重繪的邊界框越大，跨行跳轉時會直接退化成接近全螢幕的重繪。

**收緊到 4（約 128px）後，正常移動完全不受影響。**

### #7 重繪區域要分別提交，不能 union

把「上一幀區域」和「當前幀區域」union 成一個大矩形再重繪，在跨行跳轉時會覆蓋大半個編輯器。

**分開提交兩次 `repaint`。**

### #8 主控台編輯器：不能一概過濾，也不能一概接管

這一條前後錯了兩次，記錄完整結論。

**第一次的錯**：用 `EditorKind.CONSOLE` 一概過濾掉，理由是「終端機游標自帶，
掛上去只會多一個不跟隨的假游標」。**這個理由對終端機成立，對輸出主控台卻不成立** ——
Build / Run / Services / Problems 的輸出區同樣是 `CONSOLE`，
但它們的游標**恰恰是被 `CARET_COLOR` 控制的**。全域隱藏 + 一概過濾
= 這些位置的游標全部消失。

**第二次的錯**：既然不能過濾，那就給所有 `CONSOLE` 補畫游標。
結果**終端機變成雙游標** —— 終端機自己的游標本來就沒被隱藏，我們多畫了一個，
而且位置還不同步（我們讀 Editor 的 caret，終端機實際游標由模擬器維護，實測差一個字元）。

**正確做法：兩類分開處理。**

| 編輯器 | 游標來源 | 處理方式 |
|---|---|---|
| 程式碼編輯器（`MAIN_EDITOR`） | `CARET_COLOR` | 隱藏 + 拖尾 |
| 輸出主控台（`CONSOLE`） | `CARET_COLOR` | **補畫靜態游標**（不做拖尾） |
| 終端機（`CONSOLE`） | 終端機模擬器自繪 | **跳過**，什麼都不做 |

**難點在於後兩者型別完全相同**：`TerminalEditorFactory.createOutputEditor()`
回傳的就是標準 `EditorImpl`，兩者的 `EditorKind` 也都是 `CONSOLE`，靠型別無法區分。
最終改為**沿元件樹向上走訪**，命中 terminal 套件名即判定為終端機：

```java
Component c = editor.getContentComponent();
while (c != null) {
    String name = c.getClass().getName();
    if (name.startsWith("com.intellij.terminal")
            || name.startsWith("org.jetbrains.plugins.terminal")) {
        return true;   // 終端機，跳過
    }
    c = c.getParent();
}
```

用**套件名前綴**而非具體類別名，是因為終端機在近幾個版本換過實作
（`org.jetbrains.plugins.terminal` → `com.intellij.terminal.frontend`），套件名卻始終穩定。

> **教訓**：當某個操作帶**全域副作用**時，「跳過某類物件」和「放過某類物件」
> 是兩件完全不同的事。過濾條件必須回到副作用的**實際影響範圍**去核對，
> 而不能只看「這類物件自己需不需要被處理」。

### #9 殘影必須補內插點，否則只是「游標在跳」

見上文「殘影模型的實作要點」第 (a) 條。這是第一版殘影模式完全失效的原因 ——
低幀率下只有幾個相距上百像素的取樣點，視覺上就是游標在跳。

### #10 殘影模式必須額外畫常駐游標

見上文「殘影模型的實作要點」第 (b) 條。這是從彈簧模型移植時最容易漏掉的一處差異 ——
彈簧的角點永遠停在目標位置，而殘影會隨時間淡出，靜止一會兒畫面就空了。

### #11 拖尾最大長度要按「重繪代價」而非「視覺效果」來定

見上文 #6。補充一點：**跨行跳轉是最嚴苛的情境** ——
它同時放大了「拖尾拉伸」與「重繪面積」兩個因素，
調參時應當專門用它來驗證，而不是只在同一行內移動測試。

### #12 輝光不能用「居中描邊」實作

`BasicStroke` 的描邊路徑是矩形的**邊界線**，不是內部 —— 各層向外只擴 `strokeWidth/2`。

IntelliJ 游標極窄（2×32），於是最亮的那層（strokeWidth 最小）只向外擴不到 1px，
隨即被隨後填滿的不透明主體蓋住；而真正擴得夠遠的層，alpha 已衰減到 2% 以下。

**結果是「只有模糊、沒有發光」** —— 這正是最初「彈簧模式感覺不到輝光」的根因。

**正確做法**：多層同心**外擴**（填滿），而不是描邊。

### #13 光暈形狀不能用邊界框

改用外擴後，曾圖省事拿 `polygon.getBounds()` 當光暈形狀，理由是
「光暈本身是模糊的，邊界框的誤差應該看不出來」。

**這個判斷完全錯了。** 拖尾時四個角點被拉成一條斜向的細長四邊形，
而它的**邊界框**卻能覆蓋大半個編輯器 —— 跨行跳轉的瞬間，
光暈會先撐成一個巨大方塊再隨四邊形收攏而收縮，與「貼著拖尾發光」毫不相干。

**教訓**：涉及形狀的近似，必須驗證**最壞情況**（跨行跳轉），不能只看靜止狀態。

### #14 精確外擴在銳角處會失控

多邊形外擴的精確解裡，角點偏移量 ∝ `1/cos(θ/2)` —— 夾角越小，交點越遠。

拖尾時四邊形被拉成細長條，**前後兩端正是銳角**，實測偏移可達目標值的 **2.4 倍**，
光暈會從兩端甩出長尖刺。

**修正**：把偏移向量的模長截斷到 `√2`。正交處（靜止矩形）的偏移量恰好就是 √2，
不受影響；銳角處則被壓回合理範圍 —— 這也更接近真實高斯模糊對銳角的「磨圓」行為。

> 該修正的正確性由 `tools/OffsetTest.java` 獨立驗算確認 ——
> 驗證項：靜止矩形外擴量精確、中心零漂移、銳角被 √2 截斷、外擴後仍為凸四邊形。
> 用法：`javac -encoding UTF-8 tools/OffsetTest.java && java OffsetTest`

### #15 輝光尺寸不能直接套用原版的 `shadowBlurFactor`

原版 `shadowBlurFactor = 0.6` 描述的是 Canvas `shadowBlur`，即高斯模糊的**直徑**。

模糊會攤開能量，**圖形越窄，峰值被稀釋得越厲害**：VS Code 的游標有 8px 寬，
尚能撐住；IntelliJ 的游標只有 2px 寬，把同一個數值直接當作外擴半徑使用，
會得到一團寬約 40px 的橢圓霧（是游標寬度的 20 倍），完全談不上「貼著游標發光」。

**修正**：降到 `0.2`，光暈總寬約 15px。

> 這是本專案**唯一一處有意偏離原版參數**的地方。想還原那種誇張的大範圍光霧，
> 把它調回 `0.6` 即可。

### #16 靜止的游標不該有光暈

輝光是「運動中」才該有的效果。游標靜止時頂著一圈光，看起來像被一個粉色方塊框住。

**做法**：用四角相對目標的最大偏移量（即拖尾展開程度）驅動輝光強度 ——
偏移 ≤ 0.5px 視為靜止、完全跳過繪製，≥ 2.5px 為滿強度。

過渡區只留 2px 寬，是因為這兩個狀態本來就隔得很遠：
靜止時偏移為 0，而任何真實移動的偏移至少是一個字元寬（約 8px）或一行高（約 32px）。
**窄區間保證了移動時的輝光與改動前逐像素一致**，同時讓停下時的熄滅來得柔和。

### #17 不要寫死 `untilBuild`，否則外掛「只能在一個 IDE 版本上用」

早期版本的 `build.gradle.kts` 中寫的是：

```kotlin
ideaVersion {
    sinceBuild.set("252")
    untilBuild.set("252.*")     // ← 元凶
}
```

後果是外掛**只能在 2025.2 上使用** —— 2024.x、2025.1、2025.3、2026.x 全部被 IDE 拒於門外，
而使用者看到的只有一句「外掛與目前的 IDE 不相容」，完全看不出原因。

**機制**：IDE 啟動時拿 `build.txt` 裡的 build 號去比對外掛的
`since-build` / `until-build` 區間，不在區間內**直接拒絕載入**，
根本走不到程式碼執行這一步。所以這**不是 API 相容性問題，而是中繼資料宣告問題** ——
一個字的設定，效果等同於「外掛只支援一個版本」。

**正確做法**：若外掛不含版本特定程式碼，**省略 `untilBuild`**（留空即表示適用於所有更新版本）。
這是 JetBrains 官方建議。

**如何判斷自己是否「含版本特定程式碼」**：看依賴的 API 是否都是平台核心介面。
本外掛用的是 `Editor` / `CaretListener` / `EditorColors` / `EditorFactoryListener` 等，
其中「最年輕」的 `EditorKind` 也是 2016.2 就引入的 —— 這種就完全可以不設上限。

| 寫法 | 後果 |
|---|---|
| 寫死 `untilBuild` | 每次 IDE 升級都要重新發版，使用者才能繼續用 |
| 省略 `untilBuild` | 一次設定長期有效；真有 breaking change 時再收窄也不遲 |

**下限則必須實測**：`sinceBuild` 不能憑感覺放寬。除了 API 差異，還要注意**位元組碼版本** ——
本例中 2024.1 就是卡在 JBR 17 無法載入 Java 21 位元組碼上，而非 API 不存在。

### #18 「只改記憶體」不等於「不會寫入磁碟」——配色方案被無聲污染

要隱藏原生游標，只能改全域配色方案的 `CARET_COLOR`。這裡有個**想當然的推論**：

> `setColor()` 只改記憶體物件、不寫檔案 → 外掛異常結束也不會留下痕跡 → 風險可控。

前半句沒錯，**後半句是錯的**。實際發生的流程：

```
① 外掛把記憶體中的 CARET_COLOR 改成全透明
        ↓
② 使用者在 Settings 裡改了任意一項編輯器設定（本例是字型），點擊 OK
        ↓
③ IntelliJ 儲存配色方案時，把【當時的記憶體狀態】整體寫入磁碟
   → colors/_@user_Dark.icls 裡多出一行：
      <option name="CARET_COLOR" value="00000000" />
        ↓
④ 此後無論是否安裝外掛，游標都是隱形的 —— 壞值已經在磁碟上了
```

**為什麼難以察覺**：它需要「外掛正開著」與「使用者點了 OK」兩件事同時發生。而且
`partialSave="true"` 的方案檔案只記錄與父方案的**差異項**，那一行混在正常的字型設定裡，
肉眼掃過去毫無異常。本例中該檔案唯一的顏色差異項就是 `CARET_COLOR` —— 這恰恰是關鍵證據：
使用者只改了字型，游標色是被「順帶」寫進去的。

**為什麼尤其危險**：**解除安裝外掛無法自癒**。使用者遇到的現象是「我都沒裝外掛了，游標還是看不見」，
排查方向會完全跑偏到 IDE 本身。

**修復**：刪除該行，讓方案回退到父方案的值：

```xml
<scheme name="_@user_Dark" version="142" parent_scheme="Darcula">
  <colors>
    <option name="CARET_COLOR" value="00000000" />   <!-- ← 刪掉這一行 -->
  </colors>
</scheme>
```

每個 IDE 版本各存一份（`IntelliJIdea2025.2` / `IntelliJIdea2026.2` / …），**都要改**；
改之前先關掉 IDE，否則結束時會被記憶體狀態覆蓋回去。

**外掛側的防護**：`sanitizeCaretColor()` —— 讀到全透明（或 `null`）時不再當作「原始值」儲存，
因為那樣「恢復」等於把隱形原樣還回去。改用 `getDefaultForeground()` 作為後備，
讓使用者至少還能看見游標。

| 寫法 | 關閉外掛後 |
|---|---|
| `savedCaretColor = scheme.getColor(...)` | 恢復成透明 —— **游標還是不出現** |
| 先經 `sanitizeCaretColor()` 過濾 | 恢復成預設前景色 —— 游標正常 |

**教訓**：判斷「改動會不會持久化」時，不能只看**自己有沒有寫檔案**，
還要看**這個物件有沒有別的寫入磁碟路徑**。記憶體中的全域單例，隨時可能被 IDE 自己的儲存動作帶走。

## 已知限制

### 幀率天花板

**這是本專案最核心的未解問題。**

實測幀率在 **20~50fps** 之間波動（峰值可達 105fps）。

**根因不在繪製**。曾做過決定性實驗——加一個開關**完全跳過所有繪製**，只跑物理計算：

```
fps=10.9   （重繪已完全跳過）
fps=4.1
fps=4.0
fps=2.0
fps=0.4
```

**完全不繪製，幀率依然只有 2~43** —— 證明瓶頸在 **EDT 排程**，與繪製無關。

**機制**：AWT 的 `EventQueue` 中，**原生輸入事件（鍵盤／滑鼠）的優先順序高於 `invokeLater` 提交的任務**。快速移動游標時，鍵盤事件與編輯器自身重繪佔滿了 EDT，我們的渲染任務只能排在後面。

這也解釋了那個反直覺的現象：**「編輯器本身不卡，只有游標卡」**。

### 另一個反直覺現象

**大跨度跳轉反而比相鄰兩行流暢。**

原因有兩層：

1. **視覺錯覺**：同樣的幀數下，位移越大，每幀的視覺變化越明顯，越不容易察覺頓挫
2. **演算法層**：低幀率時 `dt` 較大，而短距離動畫時長恰好與之接近，會被 `DampedSpring.update()` 開頭的短路條件 `animationLength <= dt` **整體吃掉** —— 游標瞬間閃到目標，完全沒有動畫

第 2 點已透過**低幀率動畫補償**（保證至少跨越 6 幀）修復。
