## 효과

커서가 움직일 때:

- **트레일**: 커서가 불규칙한 사각형으로 "늘어남" (스프링 모델)
- **부드러운 추종**: 댐핑 스프링이 구동하며, 순간적으로 튀지 않음
- **글로우**: 가장자리를 따라 부드러운 광채 (Canvas `shadowBlur` 모사), **트레일이 펼쳐지면서 켜지고 커서가 정지하면 자동으로 꺼짐**
- **네이티브 커서 숨김**: 트레일과 겹치지 않도록

매개변수 의미는 VS Code 버전 `neovide-cursor`와 동일하게 맞췄기 때문에, 플랫폼 간 설정 이전이 쉽습니다 (유일한 예외는 [매개변수 설정](#매개변수-설정) 참고).

### 두 가지 트레일 모델 (메뉴에서 언제든 전환 가능)

| 모드 | 원리 | 특징 |
|---|---|---|
| **스프링** (기본값) | 커서 사각형의 네 모서리마다 댐핑 스프링을 하나씩 걸고, 이동 방향에 따라 서로 다른 지연 계수를 부여 → 사각형이 늘어남 | Neovide 원본 효과; 프레임 간 보간에 의존 |
| **잔상** | 매 프레임 커서의 실제 위치를 기록하고, 점점 옅어지는 잔상을 연속으로 그림 | **프레임이 떨어져도 왜곡 없음**, 낮은 프레임 레이트에서 더 안정적; 글로우가 스프링 모드보다 더 뚜렷하게 보임 |

둘은 동일한 기반 구조(오버레이 마운트, 네이티브 커서 숨김, 고정밀 스케줄링, 부분 다시 그리기)를 공유하며,
「위치 계산」 부분만 다릅니다.

## 설치

### 방법 1: Release에서 다운로드 (권장)

1. [Releases](https://github.com/yyyyolo7a79-sketch/neovim-cursor-for-jetbrains/releases)에서 최신 `*.zip` 다운로드
2. IDEA → `Settings` → `Plugins` → `⚙️` → `Install Plugin from Disk...`
3. 해당 zip을 선택하고 IDE 재시작

### 방법 2: 직접 빌드

```bash
# 요구 사항: JDK 21, Gradle 9.0+, IntelliJ Platform Gradle Plugin 2.x
./gradlew buildPlugin
# 산출물: build/distributions/*.zip
```

로컬에 이미 설치된 IDE를 사용하려면(수 GB의 배포 패키지를 내려받지 않아도 됨), `build.gradle.kts`에서 다음과 같이 수정합니다:

```kotlin
dependencies {
    intellijPlatform {
        local("D:/path/to/IntelliJIdea2025.2")   // 본인의 설치 경로로 변경
    }
}
```

## 호환성

**지원 범위: 2024.2 ~ 2026.2 이상**

| IDE | 버전 | 상태 |
|---|---|---|
| IntelliJ IDEA | 2024.2 – 2026.2 | ✅ 실측 통과 |
| CLion | 2025.2 | ✅ 실측 통과 |
| PyCharm | 2025.2 | ✅ 실측 통과 |

**여러 IDE에서 범용적으로 동작하는 이유**: 이 플러그인은 `com.intellij.modules.platform`
(플랫폼 핵심 모듈)에만 의존하며, 어떤 언어 특화 API도 건드리지 않고 IDEA Ultimate의 전용 기능에도 의존하지 않습니다.
따라서 모든 2024.2+ JetBrains IDE에 적용됩니다 ——
WebStorm / PhpStorm / GoLand / RubyMine / Rider / DataGrip 등.

### 버전 하한이 2024.2인 이유

2024.2는 플랫폼이 **JBR 21**로 전환한 기점이며, 이 플러그인의 컴파일 대상(Java 21)과 일치합니다.
2024.1 및 그 이전 버전은 **JBR 17**에서 동작하므로, Java 21 바이트코드를 로드하면 곧바로
`UnsupportedClassVersionError`가 발생하며 크래시합니다 —— 이는 바이트코드 수준의 하드 제약이며, API와는 무관합니다.

### 버전 상한을 두지 않는 이유

`<idea-version since-build="242" />`에서 **`until-build`를 의도적으로 생략**했습니다.
플러그인에 버전 특화 코드가 전혀 없어 이후 버전과도 자연스럽게 호환되므로, 비워 두면 "모든 상위 버전에 적용"을 의미합니다.

> 이는 JetBrains가 공식 권장하는 방식입니다. 상한을 고정하면(예전의 `252.*`처럼)
> **IDE를 업그레이드할 때마다 플러그인이 "호환되지 않음"으로 판정**되어, 사용자는 새 버전이 나올 때까지 기다릴 수밖에 없습니다 ——
> 이 플러그인의 초기 버전이 바로 여기서 실패했습니다. 함정 #17을 참고하세요.

### 더 이전 버전을 지원하려면?

컴파일 대상을 대상 플랫폼에 내장된 JBR 버전까지 낮춰야 합니다:

| IDE 버전 | build | 내장 JBR | 필요한 컴파일 대상 |
|---|---|---|---|
| 2022.x | 221–223 | 11 | Java 11 |
| 2023.x | 231–233 | 17 | Java 17 |
| 2024.1 | 241 | 17 | Java 17 |
| **2024.2+** | **242+** | **21** | **Java 21(현재)** |

좋은 소식은 **낮은 버전의 바이트코드는 높은 버전의 JBR에서 로드된다**는 점입니다 ——
컴파일 대상을 낮춰도 현재 지원 중인 2024.2~2026.2에는 영향이 없으며, 순수한 확장입니다.

## 사용법

- **켜기/끄기**: `Tools` 메뉴 → `Neovide 拖尾光标（开关）`
- **트레일 모델 전환**: `Tools` 메뉴 → `Neovide 光标：残影模式（低帧率更稳）`
  - **체크** = 잔상 모드; **해제** = 스프링 모드 (Neovide 원본 효과)
  - **즉시 적용**, IDE 재시작 불필요
- **성능 진단**: `Tools` 메뉴 → `Neovide 光标：性能诊断（禁用重绘）`
  - 체크하면 모든 그리기를 건너뛰고 물리 계산만 수행합니다. 「그리기가 느린지」와 「스케줄링이 느린지」를 구분하는 데 사용합니다 —— **매우 유용한 진단 수단입니다**

토글을 끄면 즉시 네이티브 커서가 복원되고 오버레이가 제거됩니다.

## 매개변수 설정

모든 매개변수는 `core/NeovideConfig.java`에 있으며, 이름과 의미 모두 VS Code 버전 `neovide-cursor.js`의 `cursorConfig`와 동일하게 맞췄습니다:

| 매개변수 | 기본값 | 설명 |
|---|---|---|
| `tailColor` | `#FFC0CB` | 트레일 색상 |
| `useShadow` / `shadowColor` | `true` / `#FFC0CB` | 글로우 켜기/끄기와 색상 |
| `shadowBlurFactor` | `0.2` | 글로우 외곽 확장 반경 = 이 계수 × 커서의 긴 변 (**원본의 0.6에서 벗어남, 이유는 함정 #15 참고**) |
| `animationLength` | `0.1` | 일반 애니메이션 길이(초), 클수록 트레일이 길어짐 |
| `shortAnimationLength` | `0.05` | 단거리 이동의 애니메이션 길이 |
| `shortMoveThreshold` | `8` | 단거리 판정 임계값 |
| `trailFactors` | `1 / 0.9 / 0.5 / 0.3` | 네 모서리의 지연 계수(트레일 늘어남의 핵심) |
| `useHardSnap` / `leadingSnapThreshold` | `true` / `0.5` | 선두 모서리 하드 스냅 |
| `maxTrailDistanceFactor` | `60` | 트레일 최대 길이 계수, 원본과 동일 (함정 #6 참고) |
| `glowLayers` / `glowOpacity` | `12` / `0.55` | 글로우의 레이어 수와 최대 강도 (**레이어 수는 밝기에 영향을 주지 않음**, 아래 「글로우 시뮬레이션」 참고) |

> `shadowBlurFactor`를 제외하면, 이 표는 원본 `cursorConfig`와 **항목별로 일치**합니다.
> 광채가 너무 크거나 작게 느껴진다면 `shadowBlurFactor` 한 값만 조정하면 됩니다:
> `0.15` ≈ 광채 전체 폭 12px (커서에 밀착) / `0.2` 기본값 ≈ 15px / `0.3` ≈ 21px / `0.6` 원본 값 ≈ 40px.

## 구현 상세 (참고용)

### 1. 마운트 지점: `contentComponent`에만 마운트할 수 있다

이 프로젝트의 **가장 중요한 결론**입니다.

실측 결과, `editor.getContentComponent()`(실제 타입 `EditorComponentImpl`)가 **유일하게 안전한 마운트 지점**입니다:

| 특성 | 왜 중요한가 |
|---|---|
| `JTextComponent`이며 **`layout`이 `null`** | `LayoutManager`가 없으면 `revalidate()` 시 다시 레이아웃하며 오버레이를 늘어뜨리는 일이 없음 |
| 좌표계가 `visualPositionToXY()`와 **자연스럽게 정렬** | 좌표 변환이 전혀 필요 없음 |

**시도했다가 반증된 마운트 지점** (모두 오버레이가 에디터 전체로 늘어나 "화면 전체가 물드는" 증상을 일으킴):

- `contentComponent.getParent()` (`JBViewport`)
- `editor.getComponent()` (에디터 패널)
- 조상 `JLayeredPane` (커뮤니티에서 제안하는 방식 — 실측 결과 실제로 존재하기는 합니다 — `EditorImpl$PanelWithFloatingToolbar` — 하지만 **이 용도로는 사용할 수 없습니다**)
- 창 루트 `LayeredPane`

### 2. 트레일 원리: 잔상이 아니라 늘어남

원본(그리고 이 프로젝트)의 핵심 메커니즘은 **여러 장의 잔상을 겹치는 것이 아니라**:

1. 커서 사각형에는 **4개의 모서리**가 있고, 각 모서리마다 X/Y 댐핑 스프링 한 쌍이 걸려 있음
2. 커서가 움직일 때 「이동 방향과 모서리 방향의 각도」로 네 모서리를 **순위 매김**(`assignRanks`)
3. 이동 방향 **앞쪽** 모서리는 큰 계수를 받고(잘 따라오며, 심지어 하드 스냅), **뒤쪽** 모서리는 작은 계수를 받음(느릿느릿)
4. 그 결과 사각형이 **불규칙한 사각형으로 늘어남** —— 시각적으로 이것이 트레일

이 설계는 잔상 방식보다 저렴하지만(점 4개만 필요), **프레임 단위 보간 정확도에 대한 요구가 높아** 낮은 프레임 레이트에서 문제가 드러납니다(아래 참고).

### 3. 잔상 모델의 구현 요점

잔상 모델은 스프링 모델보다 단순해 보이지만(위치 기록 + 그리기), **이 두 가지를 하지 않으면 성립하지 않는** 세부 사항이 있습니다:

**(a) 샘플 지점 사이에 보간점을 반드시 채워야 함**

낮은 프레임 레이트에서는 프레임당 변위가 큽니다(20fps에서는 한 번의 이동이 200px+를 건너뛸 수 있음).
샘플 끝점만 기록하면 수십~수백 픽셀 떨어진 **고립된 사각형 몇 개**만 남습니다 ——
보기에는 "커서가 튀는" 것처럼 보이고, 트레일은 전혀 없습니다.

고정 간격(`MAX_GAP_PX = 5`)으로 점을 채워야 궤적이 연속이 됩니다.
**타임스탬프도 함께 보간해야 합니다**. 그렇지 않으면 채워 넣은 점들이 같은 밝기가 되어 "딱딱한 사각형이 줄지어 있는" 모습이 됩니다.

**(b) 상시 표시되는 커서를 하나 더 그려야 함**

잔상에는 수명(`lifetime`)이 있어 만료되면 제거됩니다 ——
**커서가 잠시 멈추면 모든 잔상이 옅어져 화면이 텅 비게 됩니다**.
따라서 매 프레임 현재 위치에 alpha가 항상 1인 "커서 본체"를 하나 그려야 합니다.
(꼬리를 그릴 때 현재 위치와 겹치는 샘플 지점은 건너뛰어야 합니다. 그렇지 않으면 둘이 겹쳐 그 부분의 색이 진해집니다.)

> 스프링 모델에는 이 문제가 없습니다: 네 모서리가 항상 목표 위치에 멈춰 있기 때문입니다.

### 4. 글로우 시뮬레이션: 다층 동심 외곽 확장

Canvas의 `shadowBlur`는 진짜 가우시안 블러이고, Swing에는 이에 상응하는 기능이 없습니다. 이 프로젝트의 근사 방식은
**다층 동심 외곽 확장 + 채우기**입니다: 가장 바깥 레이어(외곽 확장량이 최대)에서 안쪽으로 레이어를 그려 나가면,
레이어 사이에서 SrcOver가 자연스럽게 누적되어 「안쪽은 밝고 바깥은 어두운」 연속 그라데이션이 만들어집니다.

**각 레이어의 alpha는 레이어 수에서 역산합니다**. 각 레이어의 독립 불투명도를 A라 하면, N개 레이어를 겹쳤을 때 가장 안쪽 레이어의 누적값은
`1 - (1-A)^N`입니다. 이것이 정확히 `glowOpacity`가 되도록 하면:

```
A = 1 - (1 - peak)^(1/N)
```

이렇게 하면 「레이어 수」와 「강도」 두 매개변수가 서로 간섭하지 않습니다 —— 레이어를 늘리면 전환만 더 매끄러워질 뿐,
**광채 전체가 밝아지지는 않습니다**.

**반지름은 선형으로 분포합니다**. 반지름 r에서의 누적 불투명도는 `1-(1-A)^k`이고, k는 그 지점을 덮는 레이어 수입니다.
반지름이 선형 분포이면 k도 선형이 되며, 계산해 보면 `r ≈ glowWidth/2` 지점에서 정확히 최대값의 약 60%까지 감쇠하는데,
이는 가우시안 곡선과 잘 맞습니다.

**광채는 사각형 자체에 밀착해야 합니다**. 이 항목은 세 번 시행착오를 거쳤습니다(함정 #12 → #13 → #14에 해당):

| 시도 | 실패 원인 |
|---|---|
| 다층 **중앙 정렬 스트로크** | 스트로크 경로는 사각형의 내부가 아니라 경계선이며, 가장 밝은 레이어는 바깥으로 1px도 채 확장하지 못하고 불투명한 본체에 가려짐 |
| **바운딩 박스**로 모양 만들기 | 트레일 시 네 모서리가 가늘고 긴 사선 조각으로 늘어나는데, 바운딩 박스는 에디터의 절반 이상을 덮을 수 있음 → 행을 넘나들 때 큰 사각형으로 부풀어 오름 |
| **정밀 외곽 확장** (최종 채택) | 각 변을 외향 법선 방향으로 평행 이동 + 인접한 변끼리 교차 계산; 예각에서는 √2로 잘라내야 함. 그렇지 않으면 긴 가시가 튀어나옴 |

**글로우는 움직일 때만 켜집니다**: 강도는 네 모서리 중 목표로부터의 최대 오프셋이 구동합니다 ——
정지 시 오프셋은 0이라 그리기를 완전히 건너뛰고; 실제로 이동할 때의 오프셋은 최소한 한 문자 폭(약 8px)
또는 한 줄 높이(약 32px)이므로, 2.5px를 최대 강도 임계값으로 잡으면 **움직일 때의 느낌은 전혀 영향을 받지 않습니다**.
자세한 내용은 함정 #16을 참고하세요.

### 5. 네이티브 커서 숨기기

IntelliJ에는 커서를 숨기는 공개 API가 **없습니다** —— `Editor` / `CaretModel` / `Caret` 세 인터페이스를
모두 `javap`로 디컴파일하여 확인했습니다(`Editor`는 `getColorsScheme()`만 제공하고 setter가 없으므로,
"특정 에디터 하나만 숨기는" 방법도 존재하지 않습니다).

유일하게 가능한 경로는 **전역 색상 구성표**를 수정하는 것입니다:

```java
EditorColorsManager.getInstance().getGlobalScheme()
        .setColor(EditorColors.CARET_COLOR, new Color(0, 0, 0, 0));
```

⚠️ **이 작업은 전역적이며, 그 대가는 직접 감당해야 합니다**: 한 번 숨기면 IDE 안 **모든** 에디터의 네이티브 커서가
사라집니다 —— 우리가 인수할 생각이 없었던 곳(Build / Run / Services 등 출력 영역)까지 포함해서요.
**숨겨진 곳은 모두 우리가 대체 커서를 그려 넣어야 하며**, 그렇지 않으면 그 위치의 커서가 완전히 사라집니다.
자세한 내용은 함정 #8을 참고하세요.

**⚠️ 반직관적인 영속화 경로**: `setColor` 자체는 확실히 메모리만 바꾸고 설정 파일에 기록하지 않지만,
**메모리 상태는 IDE에 의해 간접적으로 디스크에 저장됩니다** —— 사용자가 Settings에서 아무 편집기 설정이나 하나 바꾸고
OK를 누르면, IntelliJ는 현재 색상 구성표를 **통째로** 저장하고 투명 커서가 그대로
`colors/_@user_<구성표 이름>.icls`에 기록됩니다. 그 이후로는 **플러그인을 제거해도 스스로 낫지 않습니다**.
잘못된 값이 이미 디스크에 남아 있기 때문입니다.

이 플러그인은 이에 대한 방어를 추가했습니다: `sanitizeCaretColor()`는 "완전 투명"을 원본 값으로 저장하는 것을 거부하고,
플러그인을 끌 때 에디터 기본 전경색으로 복구합니다. 자세한 내용은 함정 #18을 참고하세요.

### 6. 고정밀 스케줄링: `javax.swing.Timer`를 쓰지 말 것

실측 데이터(Windows 11 + JDK 21):

| 타이머 메커니즘 | 실측 정밀도 |
|---|---|
| `javax.swing.Timer` (내부적으로 `Object.wait` 사용) | **15.61 ms** ❌ |
| `LockSupport.parkNanos` | 15.35 ms ❌ |
| **`Thread.sleep`** | **1.56 ms** ✅ |
| 시스템 시계 세분성 | 1.08 ms |

시스템 시계 자체는 고정밀도이지만, `Swing Timer`가 사용하는 `Object.wait`로는 그 정밀도를 얻을 수 없습니다 ——
그것이 프레임 레이트를 **64fps**에 고정시킵니다.

따라서 다음과 같이 변경했습니다: **백그라운드 스레드 `Thread.sleep` 스케줄링 + `invokeLater`로 EDT에 돌아와 그리기**.

## 함정 기록

> 아래 항목은 모두 실측으로 부딪혀 얻은 것이며, 후속 개발자를 위해 남깁니다.

### #1 `container.revalidate()`를 호출하지 말 것

`LayoutManager`가 있는 컨테이너에서 `revalidate()`는 레이아웃 관리자가 **모든** 자식 컴포넌트를 다시 레이아웃하게 만들고,
오버레이를 10×24에서 에디터 전체로 늘려버립니다 → **화면 전체가 물듭니다**.

**`repaint()`만 사용하세요.**

### #2 `paintComponent`에서 배경을 그리지 말 것

오버레이는 다각형만 그리고, **어떤 사각형 배경도 그리지 않습니다**. 이렇게 하면 실수로 늘어나더라도 다각형 자체만 보입니다.

### #3 `paintImmediately`를 쓰지 말 것 (중요)

"EDT 스케줄링 지연을 줄이자"는 생각으로 `repaint`를 `paintImmediately`로 바꿨다가 **성능이 오히려 크게 떨어졌습니다**:

| 버전 | 최대 fps |
|---|---|
| `repaint` (비동기) | **105.6** |
| `paintImmediately` (동기) | **36.9** |

원인: `paintImmediately`는 자기 영역을 동기식으로 그리는 것 외에도, **`RepaintManager`에 대기 중인 모든 더티 영역을 한꺼번에 처리**합니다 —— 텍스트 삭제 같은 작업으로 더티 영역이 많이 생기면 EDT가 오랫동안 막힙니다.

**`repaint`의 "비동기"는 결함이 아니라, `RepaintManager`가 병합과 최적화를 할 기회를 주는 것입니다.**

### #4 스프링의 감쇠 계수 `c`를 건드리지 말 것

스프링 갱신 공식에서 `c`는 감쇠 계수만이 아니라, **속도 적분에도 참여**합니다:

```java
position = (a + b * dt) * c;    // b에 이미 "속도로 인한 변위"가 포함됨
```

`c`에 하한을 두어 낮은 프레임 레이트의 느낌을 개선하려 했지만, 위치가 **반대로 증폭**되었습니다:

```
정상: c=0.135 → (100 + 4000×0.05) × 0.135 = 40.5   ✓ 감쇠
망가뜨림: c=0.5   → (100 + 4000×0.05) × 0.5   = 150    ✗ 1.5배 증폭!
```

프레임마다 누적되면 애니메이션이 그대로 **난리가 납니다**.

**프레임당 변위를 제한하려면, 결과를 계산한 뒤 `position`의 변화량을 제한해야 합니다.**

### #5 `caretPositionChanged`의 타이밍에 의존하지 말 것

텍스트 삭제 같은 상황에서는 커서 이벤트가 `visualPositionToXY()`의 데이터 갱신 **이전**에 발생할 수 있습니다 —— 이때는 이전 위치를 읽게 되고, 이후로는 새 이벤트가 오지 않아 트레일이 **영원히 예전 위치에 멈춰** 있습니다.

**올바른 방법**: 매 tick마다 커서 위치를 다시 읽고, 이벤트는 "고프레임 레이트로 깨어나는" 용도로만 사용합니다. 동시에 가벼운 `getVisualPosition()`으로 빠른 경로를 만들어, 매 프레임 비싼 좌표 변환을 하지 않도록 합니다.

### #6 트레일 최대 길이를 줄여야 함

원본 JS의 `maxTrailDistanceFactor = 60`(약 1920px)은 Canvas 전체 화면 다시 그리기에서는 문제가 없습니다.

하지만 Swing 오버레이는 **부분 다시 그리기**가 필수입니다 —— 트레일이 길수록 다시 그려야 할 바운딩 박스가 커지고, 행을 넘나들 때는 거의 전체 화면 다시 그리기로 퇴화합니다.

**4(약 128px)로 줄인 뒤로는 일반적인 이동에 전혀 영향이 없습니다.**

### #7 다시 그리기 영역은 각각 제출해야 하며, union하면 안 됨

「지난 프레임 영역」과 「현재 프레임 영역」을 union으로 하나의 큰 사각형으로 만든 뒤 다시 그리면, 행을 넘나들 때 에디터의 절반 이상을 덮습니다.

**`repaint`를 두 번 나눠 제출하세요.**

### #8 콘솔 에디터: 일괄 필터링도, 일괄 인수도 안 됨

이 항목은 두 번 틀렸습니다. 전체 결론을 기록합니다.

**첫 번째 실수**: `EditorKind.CONSOLE`로 전부 걸러냈습니다. 근거는 "터미널 커서는 자체적으로 그리므로, 여기에 마운트하면 따라오지 않는 가짜 커서만 하나 늘어난다"였습니다. **이 근거는 터미널에는 맞지만, 출력 콘솔에는 맞지 않습니다** ——
Build / Run / Services / Problems의 출력 영역도 `CONSOLE`이지만, 그곳의 커서는 **바로 `CARET_COLOR`가 제어합니다**. 전역 숨김 + 일괄 필터링
= 그 위치의 커서가 전부 사라집니다.

**두 번째 실수**: 필터링이 안 된다면, 모든 `CONSOLE`에 커서를 그려 주자. 결과는 **터미널이 이중 커서가 되었습니다** —— 터미널 자체 커서는 애초에 숨겨지지 않았는데 우리가 하나 더 그렸고, 게다가 위치도 동기화되지 않았습니다(우리는 Editor의 caret을 읽고, 터미널의 실제 커서는 에뮬레이터가 관리하므로 실측으로 한 문자 차이가 났습니다).

**올바른 방법: 두 종류를 나눠 처리합니다.**

| 에디터 | 커서 출처 | 처리 방식 |
|---|---|---|
| 코드 에디터 (`MAIN_EDITOR`) | `CARET_COLOR` | 숨김 + 트레일 |
| 출력 콘솔 (`CONSOLE`) | `CARET_COLOR` | **정적 커서 그리기** (트레일 없음) |
| 터미널 (`CONSOLE`) | 터미널 에뮬레이터가 자체적으로 그림 | **건너뜀**, 아무것도 하지 않음 |

**어려운 점은 뒤의 두 가지가 타입이 완전히 동일하다는 것입니다**: `TerminalEditorFactory.createOutputEditor()`가 반환하는 것이 표준 `EditorImpl`이고, 둘의 `EditorKind`도 모두 `CONSOLE`이라 타입으로는 구분할 수 없습니다.
최종적으로 **컴포넌트 트리를 위로 순회**하여 terminal 패키지명을 만나면 터미널로 판정하도록 변경했습니다:

```java
Component c = editor.getContentComponent();
while (c != null) {
    String name = c.getClass().getName();
    if (name.startsWith("com.intellij.terminal")
            || name.startsWith("org.jetbrains.plugins.terminal")) {
        return true;   // 터미널, 건너뜀
    }
    c = c.getParent();
}
```

구체적인 클래스명이 아니라 **패키지 이름 접두사**를 쓰는 이유는, 터미널이 최근 몇 버전에서 구현을 바꿨지만
(`org.jetbrains.plugins.terminal` → `com.intellij.terminal.frontend`) 패키지 이름은 계속 안정적이었기 때문입니다.

> **교훈**: 어떤 작업이 **전역 부작용**을 가질 때, "특정 종류의 객체를 건너뛰는 것"과 "특정 종류의 객체를 그냥 놔두는 것"은
> 전혀 다른 문제입니다. 필터 조건은 반드시 부작용의 **실제 적용 범위**로 돌아가 확인해야 하며,
> "이 객체 자체가 처리가 필요한가"만 보고 판단해서는 안 됩니다.

### #9 잔상은 보간점을 채워야 하며, 그렇지 않으면 그저 "커서가 튀는" 것

위 「잔상 모델의 구현 요점」 (a) 항목을 참고하세요. 이것이 첫 버전 잔상 모드가 완전히 실패한 원인입니다 ——
낮은 프레임 레이트에서는 수백 픽셀 떨어진 샘플 지점 몇 개만 남아, 시각적으로 커서가 튀는 것으로 보입니다.

### #10 잔상 모드는 상시 표시되는 커서를 추가로 그려야 함

위 「잔상 모델의 구현 요점」 (b) 항목을 참고하세요. 스프링 모델에서 이식할 때 가장 놓치기 쉬운 차이입니다 ——
스프링의 모서리는 항상 목표 위치에 멈춰 있지만, 잔상은 시간이 지나면 옅어져 잠시 멈추면 화면이 텅 빕니다.

### #11 트레일 최대 길이는 "시각 효과"가 아니라 "다시 그리기 비용"으로 정해야 함

위 #6을 참고하세요. 한 가지 덧붙이면: **행을 넘나드는 점프가 가장 가혹한 시나리오입니다** ——
「트레일 늘어남」과 「다시 그리기 면적」 두 요인을 동시에 증폭시키므로,
매개변수를 조정할 때는 같은 행 안에서만 이동하며 테스트하지 말고, 이 시나리오로 검증해야 합니다.

### #12 글로우는 「중앙 정렬 스트로크」로 구현할 수 없음

`BasicStroke`의 스트로크 경로는 사각형의 **경계선**이며 내부가 아닙니다 —— 각 레이어는 바깥으로 `strokeWidth/2`만큼만 확장됩니다.

IntelliJ 커서는 매우 좁아서(2×32), 가장 밝은 레이어(strokeWidth가 최소)는 바깥으로 1px도 못 가고 곧바로 이어서 채워지는 불투명한 본체에 가려집니다. 반면 충분히 멀리 확장되는 레이어는 alpha가 이미 2% 이하로 감쇠해 있습니다.

**결과는 「블러만 있고 발광은 없음」** —— 이것이 애초에 "스프링 모드에서 글로우가 느껴지지 않는다"는 문제의 근본 원인입니다.

**올바른 방법**: 스트로크가 아니라 다층 동심 **외곽 확장**(채우기).

### #13 광채 모양에 바운딩 박스를 쓸 수 없음

외곽 확장으로 바꾼 뒤, "광채 자체가 흐릿하니 바운딩 박스의 오차는 눈에 띄지 않을 것"이라는 이유로
`polygon.getBounds()`를 광채 모양으로 대충 사용했습니다.

**이 판단은 완전히 틀렸습니다.** 트레일 시 네 모서리는 대각선 방향의 가늘고 긴 사각형으로 늘어나지만,
그 **바운딩 박스**는 에디터의 절반 이상을 덮을 수 있습니다 —— 행을 넘나드는 순간,
광채가 거대한 사각형으로 부풀었다가 사각형이 오므라들면서 다시 줄어드는데, "트레일에 밀착해 발광한다"와는 전혀 무관합니다.

**교훈**: 모양을 근사할 때는 **최악의 경우**(행을 넘나드는 점프)를 반드시 검증해야 하며, 정지 상태만 보고 판단해서는 안 됩니다.

### #14 정밀 외곽 확장은 예각에서 제어 불능이 됨

다각형 외곽 확장의 정확한 해에서 모서리 오프셋은 ∝ `1/cos(θ/2)`입니다 —— 각도가 작을수록 교차점이 멀어집니다.

트레일 시 사각형은 가늘고 긴 조각으로 늘어나는데, **앞뒤 양 끝이 바로 예각입니다**. 실측 오프셋이 목표값의 **2.4배**에 달해,
광채가 양 끝에서 긴 가시를 내뿜습니다.

**수정**: 오프셋 벡터의 크기를 `√2`로 잘라냅니다. 직각 지점(정지한 사각형)의 오프셋은 정확히 √2라 영향을 받지 않고,
예각에서는 합리적인 범위로 되눌러집니다 —— 이는 실제 가우시안 블러가 예각을 "둥글게 다듬는" 동작에도 더 가깝습니다.

> 이 수정의 정확성은 `tools/OffsetTest.java`로 독립 검산하여 확인했습니다 ——
> 검증 항목: 정지 사각형의 외곽 확장량 정확, 중심 드리프트 0, 예각의 √2 절단, 확장 후에도 볼록 사각형 유지.
> 사용법: `javac -encoding UTF-8 tools/OffsetTest.java && java OffsetTest`

### #15 글로우 크기에 원본의 `shadowBlurFactor`를 그대로 적용할 수 없음

원본의 `shadowBlurFactor = 0.6`은 Canvas `shadowBlur`, 즉 가우시안 블러의 **지름**을 기술합니다.

블러는 에너지를 퍼뜨리므로, **도형이 좁을수록 최대값이 더 심하게 희석됩니다**: VS Code의 커서는 폭이 8px이라
그럭저럭 버티지만, IntelliJ의 커서는 폭이 2px뿐이라 같은 값을 그대로 외곽 확장 반경으로 사용하면
폭 약 40px의 타원형 안개(커서 폭의 20배)가 되어 "커서에 밀착해 발광한다"고 할 수 없습니다.

**수정**: `0.2`로 낮춰 광채 전체 폭을 약 15px로 만듭니다.

> 이는 이 프로젝트에서 **의도적으로 원본 매개변수에서 벗어난 유일한 지점**입니다. 그 과장된 대범위 광안개를 재현하고 싶다면
> `0.6`으로 되돌리면 됩니다.

### #16 정지한 커서에는 광채가 없어야 함

글로우는 "움직이는 중"에만 있어야 하는 효과입니다. 커서가 정지해 있는데 주위에 빛이 둘려 있으면, 분홍색 사각형에 갇힌 것처럼 보입니다.

**방법**: 네 모서리의 목표 대비 최대 오프셋(즉 트레일이 펼쳐진 정도)으로 글로우 강도를 구동합니다 ——
오프셋 ≤ 0.5px은 정지로 간주해 그리기를 완전히 건너뛰고, ≥ 2.5px는 최대 강도로 합니다.

전환 구간을 2px 폭으로만 둔 이유는, 두 상태가 원래부터 멀리 떨어져 있기 때문입니다:
정지 시 오프셋은 0이고, 실제 이동이 있으면 오프셋은 최소한 한 문자 폭(약 8px) 또는 한 줄 높이(약 32px)입니다.
**좁은 구간 덕분에 이동 중의 글로우는 변경 전과 픽셀 단위로 동일**하면서도, 멈출 때의 소등은 부드럽게 이루어집니다.

### #17 `untilBuild`를 고정하면 플러그인이 "IDE 한 버전에서만" 동작함

초기 버전의 `build.gradle.kts`에는 이렇게 적혀 있었습니다:

```kotlin
ideaVersion {
    sinceBuild.set("252")
    untilBuild.set("252.*")     // ← 주범
}
```

결과적으로 플러그인은 **2025.2에서만 사용할 수 있었습니다** —— 2024.x, 2025.1, 2025.3, 2026.x는 모두 IDE가 거부했고,
사용자가 보는 것은 "플러그인이 현재 IDE와 호환되지 않습니다"라는 한 줄뿐이라 원인을 전혀 알 수 없었습니다.

**메커니즘**: IDE는 시작할 때 `build.txt`의 build 번호를 플러그인의
`since-build` / `until-build` 범위와 비교하여, 범위 밖이면 **로드 자체를 거부**합니다.
코드 실행 단계까지 가지도 못합니다. 따라서 이것은 **API 호환성 문제가 아니라 메타데이터 선언 문제**입니다 ——
한 글자짜리 설정이 "플러그인은 한 버전만 지원"이라는 효과를 냅니다.

**올바른 방법**: 플러그인에 버전 특화 코드가 없다면 **`untilBuild`를 생략**합니다(비워 두면 모든 상위 버전에 적용된다는 뜻입니다).
이는 JetBrains의 공식 권장 사항입니다.

**"버전 특화 코드가 있는지" 판단하는 방법**: 의존하는 API가 모두 플랫폼 핵심 인터페이스인지 보면 됩니다.
이 플러그인은 `Editor` / `CaretListener` / `EditorColors` / `EditorFactoryListener` 등을 사용하며,
그중 "가장 최근"의 `EditorKind`도 2016.2에 도입된 것입니다 —— 이런 경우라면 상한을 두지 않아도 됩니다.

| 방식 | 결과 |
|---|---|
| `untilBuild` 고정 | IDE를 업그레이드할 때마다 새 버전을 배포해야 사용자가 계속 쓸 수 있음 |
| `untilBuild` 생략 | 한 번 설정하면 장기간 유효; 실제 breaking change가 있을 때 좁혀도 늦지 않음 |

**하한은 반드시 실측해야 합니다**: `sinceBuild`를 감으로 넓혀서는 안 됩니다. API 차이 외에도 **바이트코드 버전**에 주의해야 합니다 ——
이 사례에서 2024.1은 API가 없어서가 아니라 JBR 17이 Java 21 바이트코드를 로드할 수 없어 막힌 것입니다.

### #18 "메모리만 변경"은 "디스크에 저장되지 않음"이 아님 —— 색상 구성표가 조용히 오염됨

네이티브 커서를 숨기려면 전역 색상 구성표의 `CARET_COLOR`를 바꾸는 수밖에 없습니다. 여기에 **당연하다고 여긴 추론**이 하나 있습니다:

> `setColor()`는 메모리 객체만 바꾸고 파일은 쓰지 않음 → 플러그인이 비정상 종료해도 흔적이 남지 않음 → 위험은 통제 가능.

앞부분은 맞습니다. **뒷부분이 틀렸습니다.** 실제로 벌어진 경로:

```
① 플러그인이 메모리상의 CARET_COLOR를 완전 투명으로 변경
        ↓
② 사용자가 Settings에서 아무 편집기 설정이나 변경(이 사례에서는 글꼴)하고 OK 클릭
        ↓
③ IntelliJ가 색상 구성표를 저장할 때 【당시의 메모리 상태】를 통째로 디스크에 기록
   → colors/_@user_Dark.icls에 한 줄이 추가됨:
      <option name="CARET_COLOR" value="00000000" />
        ↓
④ 이후로는 플러그인 설치 여부와 무관하게 커서가 보이지 않음 —— 잘못된 값이 이미 디스크에 있음
```

**왜 알아채기 어려운가**: "플러그인이 켜져 있음"과 "사용자가 OK를 누름"이 동시에 일어나야 하기 때문입니다. 게다가
`partialSave="true"`인 구성표 파일은 부모 구성표와의 **차이 항목**만 기록하므로, 그 한 줄이 평범한 글꼴 설정들 사이에 섞여 있어
눈으로 훑어서는 전혀 이상해 보이지 않습니다. 이 사례에서 이 파일의 유일한 색상 차이 항목이 바로 `CARET_COLOR`였다는 점 —— 이것이 핵심 증거입니다:
사용자는 글꼴만 바꿨는데, 커서 색이 "덤으로" 기록된 것입니다.

**왜 특히 위험한가**: **플러그인을 제거해도 스스로 낫지 않습니다**. 사용자가 겪는 증상은 "플러그인도 설치 안 했는데 커서가 여전히 안 보인다"이고,
문제 해결 방향이 IDE 자체로 완전히 빗나갑니다.

**수정**: 해당 줄을 삭제하여 구성표가 부모 구성표의 값으로 되돌아가게 합니다:

```xml
<scheme name="_@user_Dark" version="142" parent_scheme="Darcula">
  <colors>
    <option name="CARET_COLOR" value="00000000" />   <!-- ← 이 줄을 삭제 -->
  </colors>
</scheme>
```

IDE 버전마다 각각 저장되므로(`IntelliJIdea2025.2` / `IntelliJIdea2026.2` / …), **모두 수정해야 합니다**.
수정 전에 IDE를 먼저 종료하세요. 그렇지 않으면 종료 시 메모리 상태로 덮어써집니다.

**플러그인 측 방어**: `sanitizeCaretColor()` —— 완전 투명(또는 `null`)을 읽으면 더 이상 "원본 값"으로 저장하지 않습니다.
그렇게 하면 "복구"가 투명 상태를 그대로 돌려주는 것과 같기 때문입니다. 대신 `getDefaultForeground()`로 대체하여,
사용자가 최소한 커서를 볼 수 있게 합니다.

| 방식 | 플러그인을 끈 뒤 |
|---|---|
| `savedCaretColor = scheme.getColor(...)` | 투명으로 복구 —— **커서가 여전히 나타나지 않음** |
| 먼저 `sanitizeCaretColor()`로 걸러내기 | 기본 전경색으로 복구 —— 커서 정상 |

**교훈**: "변경이 영속화될지" 판단할 때는 **자신이 파일을 썼는지**만 볼 것이 아니라,
**이 객체에 다른 디스크 기록 경로가 있는지**도 봐야 합니다. 메모리상의 전역 싱글턴은 언제든 IDE 자체의 저장 동작에 휩쓸려 나갈 수 있습니다.

## 알려진 제한

### 프레임 레이트 상한

**이 프로젝트의 가장 핵심적인 미해결 문제입니다.**

실측 프레임 레이트는 **20~50fps** 사이를 오갑니다(최대 105fps).

**병목은 그리기가 아닙니다**. 결정적인 실험을 했습니다 —— 스위치를 하나 추가해 **모든 그리기를 완전히 건너뛰고** 물리 계산만 수행:

```
fps=10.9   (다시 그리기를 완전히 건너뜀)
fps=4.1
fps=4.0
fps=2.0
fps=0.4
```

**전혀 그리지 않아도 프레임 레이트는 여전히 2~43**이었습니다 —— 병목이 **EDT 스케줄링**에 있음을 입증하며, 그리기와는 무관합니다.

**메커니즘**: AWT의 `EventQueue`에서 **네이티브 입력 이벤트(키보드/마우스)의 우선순위가 `invokeLater`로 제출된 작업보다 높습니다**. 커서를 빠르게 움직이면 키보드 이벤트와 에디터 자체의 다시 그리기가 EDT를 가득 채워, 우리 렌더링 작업은 뒤로 밀립니다.

이것은 그 반직관적인 현상도 설명합니다: **"에디터 자체는 끊기지 않는데 커서만 끊긴다"**.

### 또 다른 반직관적 현상

**대범위 점프가 인접한 두 줄 사이 이동보다 오히려 부드럽습니다.**

이유는 두 층입니다:

1. **시각적 착시**: 같은 프레임 수라면 변위가 클수록 프레임당 시각적 변화가 뚜렷해, 끊김을 덜 느낍니다
2. **알고리즘 층**: 낮은 프레임 레이트에서는 `dt`가 크고, 단거리 애니메이션 길이가 그것과 비슷해져, `DampedSpring.update()` 시작 부분의 조기 종료 조건 `animationLength <= dt`에 **애니메이션 전체가 삼켜집니다** —— 커서가 애니메이션 없이 순간적으로 목표로 튑니다

2번은 **저프레임 레이트 애니메이션 보정**(최소 6프레임을 보장)으로 수정했습니다.
